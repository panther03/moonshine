# susamune — context for agentic sessions

A speedrun-practice mod for **Super Mario Sunshine** (JP GMSJ01, US GMSE01, and PAL GMSP01). The mod's code is injected into the game at runtime — the primary distribution is a **custom Nintendont** (Homebrew Channel app) that patches the selected disc revision in memory on boot, so end users need only a real disc (or their own ISO on SD) and **no patched ISO/DOL**. Dolphin remains the primary *development* environment (via a patched `main.dol`). The companion repo `../../src/sms` is the in-progress decompilation of the game and the source of truth for any game-side type layouts; refer to it freely when sizing a struct or tracing a code path.

## Comment style

Keep comments short. Explain **non-obvious mechanics and footguns** — the
things a future reader would get wrong. Do not narrate what the code plainly
says, and never record approaches that were tried and abandoned: dead
alternatives read as relevant until they've wasted the reader's time, and they
crowd out the parts that matter. If a rationale is long, it belongs in `doc/`,
not inline.

## Repository layout

The mod sources live at the repo root (there is no longer a `susamune/` subdirectory):

- `src/*.cpp` — mod source, auto-globbed by CMake:
  - `main.cpp` — hook entry points. `onAppInit` replaces the `initialize()` call in `main()`, i.e. the last point before the app state machine (logo → title → gameplay) starts, and is where settings are made live. `onSetup` wraps `setupObjects()` on every stage load, runs the stage hooks, and at the tail of the first setup constructs the persistent menu/savestate objects after the system font and final stage heap exist. `onUpdate` then runs each frame in place of `mDirector->direct()`; `afterDraw` runs at the end of rendering and processes queued savestate loads after the game's `GXDrawDone` barrier, and `onUpdateGameMode` runs in the game-mode loop. Also holds `getArenaLo` (heap-reservation hook, see below).
  - `savestate.cpp` / `savestate.hxx` — the savestate feature. Save/load are binds (`binds.*`).
  - `menu.cpp` / `menu.hxx` — the on-screen menu: presentation and navigation only. `drawText`/`fillBox`/`fillPoly`/`strokePoly` are the shared 2D primitives; the polygon calls share one emitter and outlines use GX line width 20. Other overlays (the warp wheel) borrow them and must draw *after* `Menu::draw`, which is what leaves `mOrtho` set. A `Menu` frames a list of tabs (`MenuTab` subclasses defined inside `menu.cpp`); each tab owns its own `update`/`draw`. Uses **no heap**: the `Menu`, tabs, and JP slash-conversion buffer occupy fixed, compile-time-checked MEM2 windows, and rendering re-points one shared `J2DTextBox` at borrowed const strings each frame (the system heap is nearly full — see `getArenaLo`). The generic category tabs are QoL, Cosmetic, Misc, Savestate, UI and Timer; bespoke tabs are Creation, ILs and Binds, with Warps/Stages prepended in debug builds. Creation contains QFT, Input Display, Metadata, HUD, Custom Text and Mod Menu sections; the overlays no longer have standalone tabs. IL entries remain the selectable model, while non-selectable area headers are inserted only by its renderer. Binds inserts non-selectable section labels into its single list and C-stick left/right jumps between them; while recording it takes the pad away from the rest of the menu (`MenuTab::grabsInput`).
  - `input_display.cpp` / `input_display.hxx`, `metadata_display.cpp` / `metadata_display.hxx`, and `layout_editor.*` — the two configurable overlays. Both use the shared Creation editor; Input gives the controller elements separate colour slots, while Metadata borrows its immutable custom-format text from the MEM2 handoff. See “Settings persistence”.
  - `creation.cpp` / `creation.hxx`, `creation_extras.*` and `qft_display.*` — the heapless reusable visual-style editor shared by compact QFT, Input Display, Metadata, native HUD colours and three custom text overlays. `CreationStyle` covers position, scale, shared element/text opacity and brightness, background RGBA and optional padding; target-specific RGB arrays provide per-character or named-element colour. QFT timing remains wholly in `qft_timer.*`, including the independently persisted `QFT leading zero` toggle. START advances through All and the rendered characters/elements, while X+START goes back; selected QFT/Metadata/custom-text characters get an arrow. C-stick U/D selects an option and C-stick L/R adjusts it. Metadata reserves a maximum-width slot range for every field, even hidden ones, and right-aligns changing numeric values within their field so a digit-count change cannot transfer colours into the next row. Its editor renders every value at maximum width without forcing long labels. QFT has nine right-aligned `MM:SS.mmm` positions. Input has named colour targets for both sticks, each face button, each trigger, Start, Z, value text and the trigger outlines. Custom text uses a two-page controller keyboard and up to 32 character-specific RGB slots per word. Native HUD panes are cached after each stage setup and only touched while that same stage is fully live; streak textures use both J2D black/white endpoints, while FLUDD water uses `TGCConsole2`'s two fill colours rather than the tank artwork. Editing a native HUD image temporarily reveals only its root and target picture, then restores their prior visibility. The native Sunshine timer keeps the retail layout and rendering unchanged; its QFT section edits the 13 character colours, native streak, and TIME/TEMPO image colour and visibility. A/keep and B/discard require confirmation; Z confirms before resetting only the selected option. The editor panel docks opposite the preview and suppresses savestate and bind-driven D-pad actions. Appended style payloads sit after the ILing PB mailbox so established mailbox offsets do not move. Metadata style version 2 persists stable character overrides as `char_N_rgb`; the old flat `text_N_rgb` overrides are deliberately discarded while scalar styling migrates.
  - `mem_diagnostics.cpp` / `mem_diagnostics.hxx` — an opt-in (`ENABLE_MEM_DIAGNOSTICS`) console overlay for MEM1 testing. It verifies the root heap starts beyond the reserved region, latches corruption of four canary words in the unused scratch tail, periodically checks the stage heap, and reports current/initial/minimum free stage-heap bytes. Normal builds omit the source and all call sites.
  - `debug_warp.cpp` / `warp.hxx` — debug-only stage-warp data (`kStageNames`, `kPresets`) and logic, compiled only with `ENABLE_DEBUG_WARPS`. The menu only calls `Warp::request(...)`; `main.cpp`'s `onUpdateGameMode` polls `Warp::pending()` and calls `Warp::execute()` (flag setup + `mNextScene`) then `moveStage()`.
  - `warp_wheel.cpp` / `warp_wheel.hxx` — the Warp Wheel and the two restart binds (ports of **Instant Level Select**). Two namespaces: `LevelWarp` is the mechanism, `WarpWheel` the UI. A warp is **two-phase**: arming records a `Dest` only; `LevelWarp::kick()` (from `onUpdateGameMode`) points `mNextScene` at it, calls `moveStage()` and returns `STATE_STAGE_EXIT` (9); `LevelWarp::onDirected()` (from `onUpdate`, wrapping `direct()`'s return) writes the destination + save flags once the exit fade finishes and `direct()` finally reports a non-zero app state, then reports `CONTEXT_DIRECT_STAGE`. That split is upstream's: `direct()` only returns non-zero from the stage-exit states, so nothing can warp mid-frame. All three restart commands are ordinary wheel warps with a canned destination, so there is one code path. Instant Restart adds one step: `kick()` points `mCurrentScene` at `mPrevScene` before `moveStage()`. `TApplication::proc()` copies `mCurrentScene` into `mPrevScene` as it loads and `decideMarioPosIdx()` picks Mario's entry point from there, so this leaves the entry point untouched and Mario comes back out of the same pipe. **That write is only safe because `applyDest()` rewrites `mNextScene` at the end of the transition** — the destination follows `mCurrentScene` as well, and an earlier attempt that set it without the late rewrite loaded whatever area was named (console-verified). Upstream's separate **Instant Restart** gecko code is not ported: it blanks `mCurrentScene` instead, which is exactly what loses the respawn position it advertises. **Area Lock** rides the same tail, converting any departure into a restart of the area being left. Destinations are `(area, episode, gameInt3)` where `gameInt3` is `TFlagManager` flag `0x40003` — the parent-episode index for a secret/boss area, and what separates the five Sirena hotel scenarios (area 7) and two casino scenarios (area 14) that share one area id; `moveStage()` is the ground truth for that mapping, `data/stageArc.bin` for area id ↔ scene archive. `LevelWarp::parentArea()` is the shared internal-scene parent lookup used here and by IL attempt matching. The eight-episode wheels and their digit labels are generated. Stored wheels remain sparse: `kSlots[]` contains four-byte `{slot, area, episode, gameInt3}` records, `Wheel` is a two-byte `{first, count}` range, and `Root` is a three-byte `{episodeArea, mainWheel, subWheel}` record. Slot, wheel-title and root labels live in parallel ordered NUL pools. Static asserts bind pool counts and struct sizes and ensure the wheel ranges tile `kSlots` exactly. Uses no heap and no gecko patch: state is file statics, rendering borrows `Menu`'s `drawText`/`fillBox`/`fillPoly`. **Freezing the stage while an overlay is up** is done in `onUpdate`: `direct()` runs the movement and animation perform lists only while `mCurState` is outside the pause/stage-exit set, so the wrapper lends it `STATE_STAGE_EXIT_2` (12) for the call and restores `STATE_NORMAL` after. State 12 is the one whose own `changeState()` branch is inert until the fader is fully faded out; the returned app state is forced to 0 in case it fires anyway. `updateGameMode()` is not reached while frozen, so the pause menu cannot open either. The stage stopwatch keeps running.
  - `features.cpp` / `features.hxx` — native ports of the SMS practice gecko codes. Three mechanisms run from `featuresApply()`: Class-A `04`/`02`/`C6` writes live in one mutable flat `gFeaturePatches[]` stream; a range's `FBEGIN`/`FBEGIN_EARLY` row packs its `SettingId`, early flag, and captured/on state into the otherwise-fixed `0x80` address byte, while low address bits select halfword writes. Class-B `C2` injections live end to end in `gAsmCaves[]`; `kAsmHooks` points at each slice and packs current-on state beside its ID. The fixed Nozzle Lock and FLUDD-in-secrets multi-state sites use a specialized choice writer. Every non-early mechanism captures the live original, so Off/choice 0 restores the running revision's own word. Writes happen only on transitions and invalidate icache through `writeGameCode()`; this matters for heap sites the game rewrites itself. A code that is a `C2` plus plain writes uses both mechanisms under the same `SettingId`. Codes with real control flow or state are reimplemented as C against the decomp's types and hooks; prefer that once a code is more than a couple of writes. See `doc/gecko_porting.md` for the full guide.
  - `force_box_game.cpp` — non-destructive Box Game 1/2 selection. The `evGetSystemFlag` Sunscript call site is redirected through a wrapper that virtualizes flags `0x1005E`/`0x1005F` according to the Misc setting while leaving the real saved bits untouched; all other flags use the retail `TFlagManager::getFlag`.
  - `binds.cpp` / `binds.hxx` — configurable button combos for the mod's *actions*, built as a deliberate mirror of `settings.*`: one row in `include/susamune/binds_list.h`'s `SUSAMUNE_BIND_LIST` X-macro (enumerator + stable ini key, shared with the ARM kernel, **append-only**), one matching row in `src/binds_descs.inc` (menu label + default combo), and one `u16` of live value in `gBinds`. The description include generates an ordered NUL name pool and a parallel `u16` default-mask table. A bind is a mask of at most four GameCube button bits, matched on **exact equality** like the gecko codes it replaces; `isHeldSubset`/`wasPressedSubset` are the looser rule, for the few codes that mask rather than compare. Two actions bound to the same combo both fire -- nothing arbitrates. Binds also drive the menu toggle and savestate save/load, and are **not** silenced while the menu is open, since the menu toggle is one of them. Input comes from the raw `JUTGamePad::mPadStatus[0]` sample rather than `TMarioGamePad`, so binds still work while the game has the player's pad disabled. Also owns the combo **recorder** the menu's Binds tab drives. Persisted alongside settings — see "Settings persistence".
  - `actions.cpp` / `actions.hxx` — the bind-driven gecko-code ports (Regrab Last Held Object, Spawn Yoshi, Fast Forward), applied each frame by `actionsApply()` from `onUpdate`. Reversed and rewritten as C rather than replayed as gecko bytes; the one exception is a **ten-word trampoline** at `TEggYoshi::control+0x1C` that calls back into C, because that hook has to run once per egg in the stage and there is no global to enumerate eggs from. It is spliced in only while a Yoshi spawn is armed. **See `doc/gecko_porting.md`, "Bind-driven actions"**.
  - `settings.cpp` / `settings.hxx` — persistent mod settings, independent of the menu that edits them and the features that read them. A setting is one row in `include/susamune/settings_list.h`'s `SUSAMUNE_SETTING_LIST` X-macro (enumerator + stable ini key), one matching row in `src/settings_descs.inc` (name, choice set, default, `SettingCategory`), and one byte in `Settings::mValues`. The description include generates an ordered NUL name pool and compact two-byte descriptors; choice labels share one pool and mapping table. The menu renders/edits them generically, while `savestate.cpp` and `features.cpp` read them. Persisted to `susamune.ini` on the SD card — see "Settings persistence" below.
- `scripts/patches.py` — the hook table + memory-reservation config (addresses, mod region size, game id, region/disc metadata).
- `scripts/gen_mod_bin.py` — packs a manifest into the `mod_<vers>.bin` the launcher loads (format: `include/susamune/mod_bin.h`).
- `scripts/gen_iso_bps.py` — builds the JP/US/PAL Dolphin release patches without retail ISOs. Each `data/iso_layout_<vers>.json` contains only the few offsets, sizes and CRCs needed to grow the DOL: the FST and the one file it overlaps are relocated into existing unused disc space, while every other byte stays at its retail offset. No file names or directory listing are stored. The `layout` subcommand is the maintainer-only path for regenerating this metadata from a verified clean ISO after hook addresses change.
- `maps/<vers>.map` / `maps/<vers>.ld` — the CodeWarrior map and the linker script regenerated from it (`scripts/map_to_ld.py`).
- `include/` — reverse-engineered game headers (`include/JSystem` too).
- `scripts/` — the build pipeline (see "Build & test loop").
- `launcher/` — the custom Nintendont fork + launcher packaging.

## Injection architecture (how the mod gets into the game)

The mod is compiled + partial-linked into one relocatable object, then linked **into MEM1** at `__ArenaLo` (`0x80426020` on JP). MEM1 placement is mandatory: PPC `bl`/`b` reach only ±32 MB, so linking the blob far away in MEM2 produces "relocation truncated to fit".

The linked result is packed into **`mod_<vers>.bin`** (`scripts/gen_mod_bin.py`, format in `include/susamune/mod_bin.h`): a 32-byte header, the initialized image prefix, and the `(addr, word)` hook writes. The header separately records the full runtime image size; the kernel copies the prefix and zeroes the omitted trailing BSS on every injection, preserving every linked address while keeping zeros off the SD card. The writes ship with the code because their addresses are version-specific — an image on its own applies to nothing. The launcher reads the file for the detected disc at boot; nothing about the mod is compiled into the launcher, so one launcher serves all three revisions and the image is resident in exactly one place (MEM1) once injected.

Room for the blob is carved from the **bottom of the game's heap arena**, not the stack:

- `getArenaLo` (`src/main.cpp`) is hooked onto `OSGetArenaLo` (`0x8008dcbc`, a `PatchType.B` in `patches.py`). It returns `__OSArenaLo + SUSAMUNE_ARENA_RESERVE_SIZE`, so the root heap starts that many bytes higher and `[__ArenaLo, __ArenaLo + mod_region_size)` is free for the mod's code + data.
- **The reserve is `0x82000`, not the `0x80000` region size.** `OSInit` calls `OSSetArenaLo(__ArenaLo)` and then, when `BI2DebugFlag < 2` (true on retail discs — `bi2.bin`'s debug flag is 0), calls it again with `ALIGN32(_stack_addr)`, returning the `0x2000` debug stack to the arena. So the runtime `__OSArenaLo` is `0x2000` *below* the `__ArenaLo` the blob links at, in all three regions. Reserving only `0x80000` puts the heap floor at `MOD_BASE + 0x7E000` and the game allocates over the top `0x2000` of the region. `link_mod.py`'s `check_arena_reserve()` re-derives the gap from each map's `_stack_addr`/`__ArenaLo` and fails the build if it is not `patches.debug_stack_size`.
- `arena_reserve` is also what the manifest reports as `region_reserve`, i.e. the amount every bottom-anchored heap allocation shifts by — keep it equal to the value `getArenaLo` adds, or the Gecko-code relocation below is off by the difference.
- `SUSAMUNE_MOD_REGION_SIZE` in `include/susamune/mod_bin.h` **must equal** `mod_region_size` in `patches.py` (currently `0x80000`, i.e. 512 KiB), and `SUSAMUNE_SCRATCH` **must equal** `mod_scratch_size` (`0x40`). The runtime image has a stricter `0x58000` working cap because the rest of the region belongs to the fixed attachment heap and scratch tail. `addresses.hxx` includes the shared C header rather than spelling out a third copy, and `link_mod.py` fails the build if the C/Python constants drift.
- Every `link_mod.py` mode (`launcher`, `patch_dol`, `gecko`) prints the blob's section layout and total, and fails the build if the blob exceeds `patches.mod_blob_max_size` (currently the `0x58000` attachment-heap boundary). Tighten that one constant to enforce a smaller ceiling.
- We deliberately do **not** touch the top of the arena (the apploader stores the FST there — an earlier arena-*top* reservation overwrote the FST and crashed before the logo) and do **not** shrink the stack (that starved the scene-load stack → black screen).

`scripts/patches.py` `patches[]` also installs the actual mod hooks (`onUpdate`, `onSetup`, `afterDraw`, `onUpdateGameMode`, `onAppInit`) plus a couple of boot-speedup NOPs. Every hook is realized as a concrete `(addr, word)` write in the generated manifest.

**`onAppInit` and boot ordering.** `main()` is only `initialize(); proc(); finalize()`, and *everything* the game does — the Nintendo logo, the progressive-mode prompt, the title screen, gameplay — happens inside `TApplication::proc()`. `onAppInit` replaces the `bl TApplication::initialize` at `main + 0x1c` (`0x8000561C` on all three regions: `main` is at `0x80005600`, size `0x44`, in every map), calls the real `initialize()`, then runs `gSettings.init()`. This is the earliest point where the heap and gamepads exist but no app state has run. It matters because `featuresApply()` runs from `onUpdate`, hooked into `gameLoop()`, and `proc()` calls `gameLoop()` for the logo and title states too — settings initialised any later (as they were, from `onSetup`, which fires on *stage load*) leave every feature reading zeroed BSS for the whole boot sequence. Anything that has to be in place before `proc()` starts the app-state machine belongs here too.

**Do not patch `TApplication::proc`'s app-state jump table.** An Intro Skip port used to repoint entry 4 at the gameplay case to skip the boot logos and cutscene. State 4 is `APP_STATE_DONE`, not "the intro movie" — boot only *reaches* the intro through it, since that case sets `mNextArea` to `AREA_OPTION` and falls through into the `APP_STATE_MOVIE` body. `proc()` enters the same state whenever the app is sent back to the title, including from the console reset button (`isSomethingPushed()` → `nextState = APP_STATE_DONE`), so the redirect made reset reload the current stage instead of returning to the menu. Intro Skip is now the upstream gecko code instead (the `FBEGIN_EARLY` range in `features.cpp`), which rewrites the `APP_STATE_DONE` case *in place* to set `mCurrArea = (AREA_OPTION, 0, 0)` before branching into the gameplay body — naming the destination is what makes reset land on the title rather than on a stage reload.

**`featuresApplyEarly()`** exists for that feature: it is called from `onAppInit` and writes only the flat-stream range begun by `FBEGIN_EARLY`. `featuresApply()` does run during the logo — `proc()` calls `gameLoop()` for the logo state too — but only *after* `director->direct()`, which is already too late for the logo director; console-tested. The rest of the stream stays on the per-frame pass: a blanket early apply would let the Fast Text rows capture "originals" out of heap the game has not populated yet. An early row is **write-once and never restored** — it has no `gPatchOrig[]` slot or captured/on state, because its sites have run before the menu exists — so turning one off applies at the next boot, from the disc's own code.

## Savestate feature (savestate.cpp / savestate.hxx)

Goal: emulator-style savestates triggered by the d-pad (LEFT = save, RIGHT = load) so a runner can practice the same approach repeatedly without resetting the level. Designed to work on real Wii hardware under Nintendont — MEM2 has plenty of room beyond Nintendont's working set for a single-slot snapshot.

### Where game state lives, and what we copy

Three buckets:

1. **The stage heap** — `gpApplication.mCurrentHeap`, a `JKRSolidHeap` created in `TApplication::initialize_nlogoAfter` that fills the remaining root-heap free space. This is where almost every per-stage allocation lives: TMario, every enemy, MapObj, particles, the scene graph, the camera. We copy the whole range `[mCurrentHeap, mCurrentHeap->mEnd)`.

2. **The "game half" of `.bss` / `.sdata` / `.sbss`.** Pointers from heap-resident objects into BSS (TFlagManager singleton ptr, gpMarDirector, gpMSound, the libc rand seed, every game module's static counters) need to survive a load, so we restore the chunks of BSS that hold mutable game state.

   Boundaries are derived separately from each `maps/<vers>.map` and live in `include/susamune/addresses.hxx` (selected by the `SUSAMUNE_VERSION_{JP,US,PAL}` define CMake sets):
   - `gpApplication` only (TApplication struct)
   - game `.bss`, `.sdata`, and `.sbss` — every contiguous game-owned run in the link map, including the early Animal/Camera/Enemy/Map runs whose order differs by region
   - MSL `rand.c` `next`, the libc RNG seed (`SUSAMUNE_ADDR_LIBC_RAND_SEED`, below the sdata-game boundary; pulled in as a one-off so King Boo fruit pulls / manta patterns / enemy RNG rewind on load)

   The linker sections are not game-only: JKR / JAudio / runtime / OS / DVD / VI / PAD / CARD / GX / SI / EXI / THP / debugger state appears both before and after the game subranges depending on the retail build. We deliberately leave that state alone. Restoring OS thread queues, DVD command queues, renderer state, or audio DSP mailboxes crashes or corrupts the console.

   **Audio-module carve-out.** Each region's `kStaticRanges` excludes its `MSound.a`, `MSoundMainSide`, JAL audio-list, and THP runs in all three captured static sections. We `stopAllSound()` on both save and load, so restoring old JAudio handles or thread state would desynchronise it from the reset audio engine. The holes are map-derived and deliberately region-specific because the retail link order differs substantially.

3. **Tracked root-heap allocations** (the `kPointedAllocs` table). The `JKRSolidHeap` snapshot does NOT cover the root heap — there's a swath of allocations made in `TApplication::initialize()` (TFlagManager, gamepads, fader, rumble manager, ...) that live on the root heap before the JKRSolidHeap starts. The pointers to them are in BSS and get preserved by bucket 2 above, but the pointed-to bytes need a separate snapshot. For each one we follow the pointer at save time and capture the target as another region.

   Current table (savestate.cpp `kPointedAllocs`):

   | name | pointer addr | size | notes |
   |---|---|---|---|
   | TFlagManager | `0x8040a290` (`TFlagManager::smInstance`) | `sizeof(TFlagManager)` = 0x380 | Fixes coin counts, shine flags, episode flags |
   | TTimeRec | `0x8040a2f8` (`TTimeRec::_instance`) | 0x820 (the 0xDFC0 in `TTimeRec::start` is a config arg, not the size) | Input/profiler recorder |
   | SMSRumbleMgr | `0x8040a248` | `sizeof(RumbleMgr)` = 0x30 | Rumble channels' active state |
   | Pad0..Pad3 | `0x803e6020 + 4*i` (`gpApplication.mGamePads[i]`) | `sizeof(TMarioGamePad)` = 0xF0 | Fixes controller-stuck-disabled bug after loading from dialog |
   | Fader | `0x803e6034` (`gpApplication.mFader`) | `sizeof(TSmplFader)` = 0x38 | Fixes crash when loading during shine-spawn / shine-get / blue save screen fade transitions. The `TSMSFader` header previously omitted two fields (`_30` at 0x30 = current wipe type, `_34` at 0x34 = wipe progress float), so `sizeof` evaluated to 0x30 instead of the real 0x38. The wipe-type field at 0x30 controls which rendering path `draw()`/`drawFadeinout()` take and is passed to `Hx_GetWipeType`; the global wipe-system state (`hx`/`hx_buffer` in BSS) IS snapshotted, so a stale `_30` left it out of sync with the restored global state and crashed on the next `draw()`. |

### What we deliberately do NOT snapshot

- **`.data`** — almost entirely vtables and static const tables, read-only at runtime.
- **stack** — we're running on it.
- **System storage outside the game-only ranges** — JSystem / JAudio / OS / DVD / VI / PAD / CARD / GX / SI / EXI / THP / TRK. Hardware-tied or kernel-tied state.
- **Audio** — `gpMSound`'s playing-sounds list references DSP-side state we can't snapshot. We call `gpMSound->stopAllSound()` before BOTH save and restore, and exclude the audio-owned static runs in every region. Music re-triggers naturally on the next stage event.
- **`gpCardManager`** — has its own worker thread + mutex + cond var on the root heap. Byte-copying those would trash kernel-side bookkeeping. A queued load stays pending while `getLastStatus() == CARD_ERROR_BUSY`, checked once per rendered frame, and gives up after 600 frames; counting scheduler yields here is wrong because hundreds can elapse before one card transaction finishes. (The launcher disables memory-card *emulation* by default — see below — but the game still runs the same CARD code paths against real/absent EXI.)

### Invariants enforced before load

- Snapshot magic matches (`'SUSA' = 0x53555341`)
- Snapshot version matches (`kSnapshotVersion`, currently 13; bump when the layout breaks)
- Snapshot region matches (`game_version` in the header vs `SUSAMUNE_GAME_VERSION`) — a JP snapshot won't load on a US/PAL build and vice versa
- `gpApplication.mCurrentHeap` is at the same address as save time (heap moved → all pointers stale)
- Heap size matches
- Area + episode IDs match — same-scenario only. Cross-scenario would have to deal with `freeAll()` between directors.
- The region count, contiguous payload offsets, destinations and sizes exactly match the compiled static ranges, current tracked root allocations, and final stage-heap range. The whole manifest is checked before the first restore write, so a damaged MEM2 header cannot turn into an arbitrary `memcpy`.
- **Not in a load/intro transition** (`inLoadTransition()`): refuses while `gpMarDirector->_260 == 0` (the async setup thread is still populating the heap — the all-black loading screen) or while `mCurState < STATE_GAME_STARTING` (the black init + intro-cutscene states 0/1). It is allowed from `STATE_GAME_STARTING` (2) onward — i.e. as soon as the opening wipe fades the stage back in and Mario plays his materialise-in animation, since the whole stage is loaded and nothing streams in dynamically by then.

### Where the snapshot buffer lives

In MEM2. Configured via `kSnapshotBase` near the top of `savestate.cpp`, gated on the `IS_EMULATOR` define set by the CMake `IS_EMULATOR` option:

- **Dolphin** (`#if IS_EMULATOR`): `0x70000000` — emulator's "free" space.
- **Wii (Nintendont)**: `0x91F00000–0x92F00000` — a dedicated 16 MB window whose exclusive end is the Nintendont ARM kernel. `include/susamune/mem2_map.h` is the shared source of truth for both PPC aliases and ARM physical addresses; compile-time adjacency/alias checks prevent launcher buffers from entering the window.

Buffer is sized at 16 MB reserved (`kSnapshotReservedSize`). Layout: a 0x120-byte header (magic, version, heap addr/size, area/episode, feature state, and region table) at the base, then the region payloads packed back-to-back. A load reconciles the restored Fast Text/Fruit-timeout patch bytes with the settings that are live now; the snapshot never rewinds the user's current settings.

## Settings persistence (`susamune.ini`)

Settings survive a power cycle by living in a plaintext `susamune.ini` at the root of **the device the launcher was run from** — not the device the game is read from, which can be the other one or a real disc. The PPC (mod side) cannot do file I/O — storage belongs to the ARM side — so the launcher owns both directions and the mod talks to it through a MEM2 mailbox.

**There is exactly one `susamune.ini`, and the kernel will mount a second volume to reach it.** The kernel used to mount one FAT volume, the game's, and read the ini from it; that meant an ISO on USB and a launcher on SD needed two copies of the file. Now drive 0 is the game/storage device (every pre-existing unprefixed kernel path still binds to it, unchanged) and drive 1 is the launcher's device, brought up *only* when the two differ — `SusamuneCfgIniPath()` (kernel/main.c) is what picks `"1:/susamune.ini"` over `"/susamune.ini"`. `NIN_CFG_CFG_ON_USB`, set by the loader from `launch_dir`, is how the kernel learns which device that is. `_VOLUMES` is 2 on both sides now (`launcher/fatfs/ffconf.h`) and `kernel/diskio.c` dispatches per drive, but only once a second volume exists: with one volume `disk_read`/`disk_write` still point straight at that drive's driver, so the ISO streaming path is untouched in the common single-device case. FatFS is non-reentrant and shared with the DI thread, so writes to either drive stay under the existing "no async disc read in flight" guard.

**Settings, binds and overlay configs are per game version.** One launcher serves GMSJ/GMSE/GMSP, and a JP route's configuration is not a PAL route's, so the six sections carry a region tag: `[settings_<region>]`, `[binds_<region>]`, `[input_display_<region>]`, `[metadata_display_<region>]`, `[qft_display_<region>]`, and `[creation_<region>]`. Only the running disc's sections are parsed — the handoff block holds **one** region's configuration, not three — which is why a save cannot re-emit the file from the block. See the copy-through note below.

**The pieces:**

- `include/susamune/settings_list.h` — the `SUSAMUNE_SETTING_LIST(X)` X-macro: one `(enumerator, ini_key)` row per setting, included by the mod (to build `SettingId`) and by the ARM kernel (to build its key table; the mod reads values by index and never materialises the keys). Single source of truth, so the two cannot drift. **The row order is the on-disc `values[]` layout, so the list is append-only** — reordering silently reinterprets every saved file. Ini keys are deliberately separate from the menu display names in `src/settings_descs.inc`, so relabelling a menu entry never invalidates a user's file.
- `include/susamune/binds_list.h` — the same arrangement for binds: `SUSAMUNE_BIND_LIST(X)` (one `(enumerator, ini_key)` row per bindable action, **append-only** for the same reason) plus `SUSAMUNE_BIND_BUTTON_LIST(X)`, the `(button bit, ini token, menu glyph)` table both sides use to spell a combo. Binds live in a `[binds_<region>]` section as `+`-joined tokens (`regrab_object = X+DUp`) rather than as a number, so the file stays hand-editable.
- `include/susamune/susamune_cfg.h` — the `struct SusamuneCfg` handoff block, shared by all three toolchains (plain C, no type dependencies; the ARM kernel and the PPC are both big-endian, so no byte swapping). Lives at `SUSAMUNE_MEM2_CFG_*` = `0x92EF0000` / phys `0x12EF0000`, 64 KiB carved off the top of the snapshot window (whose 16 MiB reservation far exceeds its use). **Deliberately outside the snapshot payload, so a savestate load does not rewind the user's settings.**
- `launcher/kernel/SusamuneCfg.c` — the parser and serializer, on the ARM side.

**Flow:**

1. **Boot** — `SusamuneCfgInit()` runs from the kernel's `main()` right after `DIinit(true)` — which is what publishes `GAME_ID`, and the region tag selects which sections to read — and before the PPC is released. It parses this version's sections of `/susamune.ini` into the block and stamps magic/version/count. Unset entries are `SUSAMUNE_CFG_UNSET` (`0xFF`). A disc with no mod leaves the block zeroed, which the mod reads as "no launcher".
2. **Load** — `Settings::init()` (from `onAppInit`, see above) installs compiled-in defaults, invalidates the block, validates magic+version, and adopts settings, binds, and overlay configuration. Settings and overlay scalar fields move into MEM1. Input reconstructs its stable 32-byte wire payload from a compact live config on save. Metadata borrows the launcher-published custom format directly from the immutable MEM2 payload; its original 256-byte wire config remains fixed and an appended style payload stores Creation fields plus 256 character RGB slots. QFT's fixed 64-byte payload stores the same style concepts for nine slots plus its leading-zero toggle. The appended Creation payload stores explicit native-colour presence bits and three fixed-size custom-word records without moving older mailbox offsets. Presence masks keep 255 valid both as a colour value and as the no-background padding sentinel. Hot setting reads remain cached MEM1 loads.
3. **Save** — closing a dirty menu stages settings, binds, Input, Metadata, QFT and Creation configs into the block, bumps `saveSeq`, and returns immediately. The kernel's main loop sees `saveSeq != ackSeq`, rewrites the ini, and answers with `status` (a FatFS `FRESULT`) + `ackSeq`. The mod polls that from `Menu::update` and toasts the result.

**Things to keep in mind when touching this:**

- **Cache-line ownership.** The PPC flushes whole 32-byte lines, so a field the ARM writes must never share a line with one the PPC writes — a PPC writeback would clobber the ARM's newer value with a stale copy. Hence the padding in `SusamuneCfg`: line 0 is mod-owned (`magic`/`version`/`count`/`saveSeq`/`flags`), line 1 is kernel-owned (`ackSeq`/`status`), and lines 2+ hold the shared configuration payload. The IL PB sub-mailbox has its own control, ack, and payload cache lines. `SusamuneCfgService()` therefore flushes *only* `&cfg->ackSeq, 32`. `__builtin_offsetof` checks in the header fail the build if the layout drifts.
- **The kernel services the doorbell under the same guard as `GCNCard_Save`** — only when no async disc read is in flight, because FatFS is shared with the DI thread. It sits *ahead* of the card branch in the `else if` chain, since that one is on a 60-second timer and would otherwise starve settings writes.
- **First boot writes the file from the mod, not the kernel.** Defaults live in `src/settings_descs.inc`, `src/binds_descs.inc`, and the overlay implementations; duplicating them in the launcher would create another source of truth. So when the ini is missing *or has no configuration for the running version* the kernel raises `SUSAMUNE_CFG_FLAG_NO_CONFIG` and `Settings::init()` answers with a `save()`, filling in that version's sections without disturbing the others.
- **A save is a transactional copy-through, not a regeneration.** `WriteIniFile()` completely reads the old file and re-emits every line into `susamune.ini.tmp`, substituting freshly written sections in place of this version's six. After a successful close and size check it rotates the old main file to `.bak` and installs the temp; boot recovery restores the backup only when the main file is absent. That keeps the other versions, `[nintendont]`, comments, and unknown sections byte-for-byte without materialising them. Unrecognised keys *inside our own six sections* are still dropped. Oversized, incomplete, read-only, or structurally aliased files are refused before the main file is replaced; a settings read error is fail-closed so compiled defaults cannot overwrite a valid file that was merely unreadable.
- **Forward compatibility** is via `count` (and `bindCount`): a kernel older than the mod carries fewer settings, and the remainder keep their compiled-in defaults. That is what makes appending a setting safe without a version bump. Binds were added the same way — a pre-binds kernel memsets only as much of the block as it knows about, so `bindCount` reads back as 0, meaning "nothing persisted, keep the defaults".
- **Emulator persistence uses slot B.** `Settings::init()` installs defaults before `proc()`; the first `onUpdate` after Sunshine constructs its slot-A manager calls `finishInit()` and reads `susamune_settings` from slot B before that director's `direct()`. The file uses game/company IDs `GMSJSU`, `GMSESU`, or `GMSPSU`, so it is distinct from Sunshine's `GMS?01` save while remaining visible to Dolphin's current-game-only GCI-folder mode. Two checksummed 8 KiB generations protect the previous settings/PB snapshot from interrupted writes. The initial read borrows 48 KiB from the boot heap and immediately releases it. Later writes are queued until Sunshine's card worker has been observed idle after two director passes, then borrow its CARD buffers under the manager mutex. The write preserves Sunshine's last status; its slot-A manager is unmounted only while the buffers are borrowed and remounts automatically on its next operation. Slot A's disk ID and file are never changed. Missing, unformatted, or incompatible slot-B storage falls back to defaults and `SETTINGS_SAVE_UNSUPPORTED` without formatting anything.

## Known issues / open work

- **FIXED: console NPC-talk/pause load hang.** Loading during the Pianta-handed shine animation (Pianta Village ep 3/6, Sirena Beach ep 6), and loading from the pause menu in Pianta Village ep 6, used to hard-hang the console. The cause was mid-frame restore ordering: D-pad loads ran from `onUpdate`, after `director->direct()` but before the same frame's fader update/draw, `gpMSound->mainLoop()`, and rendering. Those systems consumed a mixture of restored game state and live audio/GX state. D-pad loads are now queued until `afterDraw`, immediately after the game's `THPPlayerDrawDone()`/`GXDrawDone()` barrier; `loadState()` also enforces its own `GXDrawDone()` and invalidates the texture cache after restore. All four original reproductions were confirmed fixed on Wii hardware. Relocating every Nintendont user out of the snapshot window did **not** resolve this particular hang, but the collision was real and the exclusive MEM2 ownership is retained as a separate correctness fix. Historical observations:
  - **Console only** — cannot reproduce on Dolphin (its permissive memory map tolerates whatever real hardware faults on).
  - The last on-screen status remains `saved`, but that does **not** prove the restore loop itself wedged: `loaded` is rendered only later, after the restored fader/audio state is used again in the same frame.
  - **Not a bad restore-write address.** A temporary guard that validated every restore target against MEM1 (`0x80003100–0x81800000`) and reported out-of-range regions as `R<i> <addr>` never fired — every `r.addr`/`r.size` we write is in range. So it's not a captured pointer resolving to an unmapped address on our side.
  - **No exception dump.** Nintendont installs its own exception handler, so there's nothing on screen, and an `OSSetErrorHandler` overlay from the mod (record SRR0/DAR, skip the faulting instruction, resume so the render loop shows it) never displayed — Nintendont's handler wins and/or the resume didn't take. `OSFatal` isn't linked in the game either.
  - **Ruled out:** the SMS audio-module BSS (carving it out of the snapshot — see the audio carve-out above — did *not* fix this, though it's kept as a correctness improvement); and all shine/talk/demo/event-interpreter state, which the decomp shows is entirely in the captured stage heap.
- **Memory-card emulation remains incompatible with the Susamune MEM2 layout.** It is disabled by default. Stock Nintendont anchors card data at `0x91000000` and can grow into the relocated buffers below the snapshot; do not define `ENABLE_MEMCARD_EMU` without designing another placement.
- **Async DVD load mid-snapshot** — there's no `JKRDvdRipper::isIdle()`-style check. If a snapshot is taken mid-archive-load, you'd capture an inconsistent heap. In practice gameplay is quiescent, but a robust version would gate on this.
- **Cross-scenario load** is refused. To support it we'd need to trigger the same boot-time setup the game's stage transition does — much more involved.
- **Loading restarts audio silent** — sounds and BGM that were playing at save time are stopped, not resumed. The next stage event re-triggers them, so it usually self-corrects within a second. If we want true seamless audio resume, we'd need to capture the active BGM ID separately and re-issue it.

## How to extend

**Adding a new tracked root-heap allocation:**
1. Find the global pointer's address in `maps/<vers>.ld` (e.g. `grep -n "Symbol__" maps/jp.ld`).
2. Determine the pointed-to size — usually `sizeof(SomeClass)` after including the header.
3. Add an entry to `kPointedAllocs` in `savestate.cpp`.
4. `kMaxRegions` is computed automatically; the build verifies that `SavestateHeader` fits its current `0x120`-byte reserved header.

**Adding a new static range** (e.g. some BSS modules in the OS half turn out to be safe to snapshot): add to `kStaticRanges`. The load loop is uniform, no other changes needed. The trailing `gate` field is `kNoGate` for an always-captured range, or a `SettingId` that must be enabled for the range to be captured (this is how `SETTING_SAVE_RNG_STATE` excludes the RNG seed).

**Adding a new setting:** append a row to the global tail of `SUSAMUNE_SETTING_LIST` in `include/susamune/settings_list.h` (enumerator + stable ini key) and a matching row at the same ordinal in `src/settings_descs.inc` via `SBOOL(name, default, category)` or `SCHOICE(name, default, CHOICES_*, category)`. **Append only** — the list order is the on-disc layout (see "Settings persistence"); category grouping comes from the descriptor and must never be created by inserting an ID. Add a choice-set pool/map entry only when a new set of labels is needed. The enum, menu filtering, launcher's key table, and live values array follow automatically, and a `static_assert` catches a list/descriptor count mismatch. Features read it via `gSettings.get*`.

**Adding a new bind:** append a row to `SUSAMUNE_BIND_LIST` in `include/susamune/binds_list.h` (enumerator + stable ini key) and a matching row at the same ordinal in `src/binds_descs.inc` (menu label + default combo). **Append only**, for the same reason settings are. The enum, Binds tab, launcher's key table and MEM2 `binds[]` layout all follow from the list. Read it from an action with `gBinds.wasPressed(id)` / `gBinds.isHeld(id)`.

**Adding a new menu tab:** define a `MenuTab` subclass in `menu.cpp` (implement `title`/`update`/`draw`, keep per-tab cursor state in the object), give it a static BSS buffer next to the others, and add one `mTabs[mNumTabs++] = new (buf) YourTab();` line in `Menu::Menu()`. A new generic setting category also needs a title-pool offset, buffer and constructor entry. A tab that needs the pad to itself (the Binds tab, while recording a combo) overrides `grabsInput()`. `kMaxTabs` caps the count; the tab strip scrolls horizontally when titles overflow. Tabs draw via `Menu::drawText` / `J2DFillBox` and must not allocate.

**Adding a new hook:** add an entry to `patches[]` in `scripts/patches.py`. A `B`/`BL` row uses `sym` naming an implemented `extern "C"` symbol in `src/`; a `W32` row uses `val` and has no symbol. The manifest/launcher/dol/gecko targets all pick it up automatically.

Mod code/data use individual sections and the final link uses `--gc-sections`; every `B`/`BL` hook in `patches[]` is rooted with `--undefined=<sym>` because manifest writes are not ELF references. Adding a hook through `patches[]` therefore both emits and retains it. `-fmerge-functions` may give byte-identical functions the same address, so function-address identity must not be relied upon.

**Bumping the snapshot format**: increment `kSnapshotVersion`. MEM2 is volatile across power cycles, so there's no data migration concern; the version field exists to invalidate stale snapshots left in MEM2 by a different build of the mod.

## Launcher (custom Nintendont) — `launcher/`

`launcher/` is a Nintendont fork: an **ARM kernel** (`launcher/kernel`, built with devkitARM) plus a **PPC loader/GUI** (`launcher/loader`, built with devkitPPC + libogc). Packaged as the HBC app `susamune_launcher/{boot.dol, icon.png, meta.xml, mod_jp.bin, mod_us.bin, mod_pal.bin}` — **one app for every disc revision**.

Key modifications from stock Nintendont:

- **Mod injection is a runtime file load, split across both sides.** The **loader** (`launcher/loader/source/SusamuneMod.c`) reads `<launch_dir>/mod_<region>.bin` for `ncfg->GameID` into the MEM2 staging area and flushes it; the **kernel**'s `PatchSusamune()` (called from `PatchGame` after `DoPatches`) validates the header against the running `GAME_ID`, copies the initialized prefix into MEM1 at `baseAddr & 0x7FFFFFFF`, zeroes the remaining runtime image, synchronizes the full range, and applies the writes that came with it.
  - **The loader does the file I/O, not the kernel.** It already knows the game id for every boot path (game list, `di:`, Wii VC) and still has both FAT devices mounted; the kernel mounts only one volume and only learns the disc id after `DIinit`. `launch_dir` is the loader's own directory, which is what makes "next to boot.dol" work.
  - **The staging area costs no persistent memory.** It is the tail 132 KiB of the 6 MiB `patch.bin` handoff buffer (`SUSAMUNE_MEM2_MODBIN_*` in `mem2_map.h`) — same loader-to-kernel lifetime, dead the moment the copy into MEM1 lands. Deliberately *not* taken from the snapshot window, whose payload can legitimately grow to fill its reservation. This is the whole point of the file-based design: the blob used to live permanently in `kernel.bin` **and** in MEM1.
  - **The header is always written, even with no file**, because MEM2 survives across app launches and a stale blob would otherwise be injected into an unrelated game. A missing/invalid/mismatched header simply means "run the game unmodified", which is also what a standalone launcher build does.
  - The bin is untrusted SD-card input: the loader requires the computed `header + codeSize + writes` length to equal the bytes read, then `SusamuneModStaged()` independently validates regional base/reserve, `codeSize <= memSize`, alignment, write count, and staging/runtime bounds before anything is copied.
- **Gecko-code relocation** — the mod raises the arena floor by `arena_reserve` (`0x82000`), shifting every bottom-anchored heap allocation up by that much, which breaks Gecko practice codes that write to *hardcoded heap addresses*. `PatchSusamuneGeckoCodes()` (Patch.c, called right after the `.gct` is copied to `cheats_start`) recognizes the full regional DPad Functions code tails (`dpad.txt`, `dpad_us.txt`, and `dpad_pal.txt`) via `RelocateSusamuneGeckoSignature()` and bumps only their message-buffer writes by the staged bin's `arenaReserve` (the manifest's `region_reserve`, which is `arena_reserve` — the amount `getArenaLo` actually adds, *not* `mod_region_size`). With no mod staged the codes are left alone, since nothing shifted the heap. The long, region-specific signatures make false matches implausible. Add more `(signature → relocate)` entries here if other absolute-heap-address codes need it; the general alternative is a top-of-arena reservation (keeps bottom-anchored data at stock addresses, no per-code signatures). **Ported** codes need the same shift applied on the mod side — `FHEAP`/`FHEAPLO` in `src/features.cpp` add `SUSAMUNE_ARENA_RESERVE_SIZE` to a patch row's address (Fast Text's message-buffer writes are the only users today).
- **The loader GUI is susamune's, not Nintendont's** (`launcher/loader/source/SusamuneMenu.c`). Three screens: a centre-justified main menu (Launch Game / Version / Path / Settings), a file browser rooted at the device list with a "Disc Drive" pseudo-entry, and a one-column settings screen with help text under a rule. The stock game-list and two-column settings menus are gone. Launching with no path configured refuses and blinks the red `<not set - press A>` sentinel; launching an image whose header disagrees with the selected Version refuses with a message. A real disc can only be checked after `DIinit`, so that one lands in `main.c` just after the disc header read.
  - **Two rendering/FS footguns, both fixed and both easy to reintroduce.** `GRRLIB_Render()` ends with its own `VIDEO_WaitVSync()` (twice in progressive), so a loop that also waits at the top runs at half rate and visibly judders — draw, render, done. And `f_opendir` rejects a **trailing slash**: `create_name()` parses the empty segment after it and returns `FR_INVALID_NAME`, which silently reads as "empty directory". The browser carries paths *with* the slash because that is what child paths are built from, so `ReadDirectory()` strips it before opening (except at a device root, where `sd:/` needs it).
  - **Input had to be un-stubbed first.** Every `FPAD_*` in `launcher/loader/source/FPad.c` had its body commented out, which is why the picker "didn't work with the controller setup on this fork" — the menu was fine, nothing ever reported a press. GC pad, HID and the DRC are restored; **Wiimote/WUPC stays gutted deliberately** (it is used for in-game reset handling).
- **No `nincfg.bin`.** The kernel only reads it as a fallback when the MEM2 `NIN_CFG` handoff is invalid (`kernel/Config.c`), and the loader always provides that, so the file was pure loader-side persistence. `susamune.ini`'s `[nintendont]` section replaced it: `version`, `path_jp`/`path_us`/`path_pal`, `native_controls`, `unlock_read_speed`, `enable_cheats`, `language`. `NIN_CFG` is built fresh each boot from compiled-in defaults plus those keys — it is the *transport* to the kernel, never a second place a setting lives. `launcher/loader/source/SusamuneIni.c` parses and rewrites the section as a copy-through, the mirror image of what `SusamuneCfg.c` does to the mod's sections.
- **No command-line arguments.** The base64 `NIN_CFG` blob, the `sd:/`/`usb:/`/`di:` path forms and `--cheats`/`--noIPL`/`--mcd` are gone, along with the `argsboot` flag that suppressed the status screens. `argv[0]` is still read, for `launch_dir` — that is how `mod_<region>.bin` is found next to `boot.dol`, and now also how the launcher's own device is identified.
- **Auto Boot** (`autoboot` in the ini, `NIN_CFG_AUTO_BOOT` to the kernel) skips the menu and boots the configured version directly. **B cancels it**, following the button Nintendont's own autoboot used; the pad is polled for ~200 ms rather than sampled once, because the pads have only just been initialised. Its point is speed, so **devices are mounted lazily**: the launcher's own device first (the ini is there and nothing can be decided before reading it), then only the game's device if that is the other one. Bringing up USB costs seconds — `devInitInfo` gives it a 10 s init timeout — so an all-SD auto boot must never touch it. The menu path mounts both, since it lists them. Any failure (no path for this version, file missing, wrong region) falls through to the menu with the reason in `ErrorLine`; the exception is a wrong *disc*, which is only detectable after `DIinit`, by which point the menu is behind us — that one gets a message naming the B-at-startup escape.
- **Real-disc (RealDI) boot** — select `Disc Drive` as the path for a version, which stores `di` and is what the kernel keys off to init RealDI. The RealDI disc buffer was relocated into the ISO-cache region (`0x11000000`, shrunk to 3 MB) so it no longer collides with the savestate mod's MEM2 window at `0x91F00000`.
- **Reserved savestate MEM2 window** — `include/susamune/mem2_map.h` packs the 3 MB ISO/RealDI cache and all relocated Nintendont scratch/handoff buffers below physical `0x11F00000` (the last 132 KiB of that, `0x11EDF000`, being the mod-bin staging area), reserves physical `0x11F00000–0x12EF0000` exclusively for the snapshot and `0x12EF0000–0x12F00000` for the settings block, and places the ARM kernel at `0x12F00000`. The loader uses cached `0x9xxxxxxx` aliases; the kernel uses physical `0x1xxxxxxx` addresses. `launcher/mem_map.txt` documents the same layout.
- **Kernel ZIP inflation is direct to its final MEM2 window.** `unzip_data_into()` bounds the embedded image at the `0x12FE0000` ARM-stack boundary, loops over partial reads, and checks the archive CRC. Do not reintroduce a heap buffer plus `memcpy`: it cost one complete kernel image at startup and provided no ownership barrier.
- **Memory-card emulation disabled by default** — `launcher/loader/source/main.c` clears `NIN_CFG_MEMCARDEMU | NIN_CFG_MC_MULTI` and zeroes `MemCardBlocks` under `#ifndef ENABLE_MEMCARD_EMU`, *before* the card-file init and the kernel handoff. This skips the loader's card-file creation and the kernel's `GCNCard_Load` (both flag-gated), so no card file is created and no emulation code runs; the game falls back to real-EXI/SRAM (reports no memory card). The stock emulation buffer overlaps the packed MEM2 layout; do not define `ENABLE_MEMCARD_EMU` without first assigning it a non-overlapping region and adding that region to `mem2_map.h`.
- **Settings persistence** — `launcher/kernel/SusamuneCfg.c` parses `susamune.ini` into the MEM2 settings block before the game boots and rewrites it on demand from the main loop. See "Settings persistence" above. The loader owns `[nintendont]` and the kernel owns `[settings_<region>]`, `[binds_<region>]`, `[input_display_<region>]`, `[metadata_display_<region>]`, `[qft_display_<region>]`, and `[creation_<region>]`; each transaction copies the other's sections through verbatim. Loader and kernel writes occur in separate boot/gameplay phases, and both use the same temp/backup recovery protocol.
- **"Unlock Read Speed" defaults to on** — it is `unlock_read_speed = 1` in `kIniDefaults` (`SusamuneIni.c`), so a fresh card has read-speed unlocking without the user visiting Settings.

### How the launcher build is structured (CMake)

The launcher spans three cross toolchains and CMake binds one compiler per build tree, so `launcher/CMakeLists.txt` is a **super-build**: it configures three `ExternalProject`s, one per toolchain group, each with its own toolchain file under `launcher/cmake/`:

- **ppc** (`toolchain-devkitPPC.cmake`, bare `powerpc-eabi-`): `multidol`, `resetstub`, `PADReadGC` (loader/source/ppc), the `kernel/asm` PPC code blobs, `codehandler`, and `fatfs-ppc`. Produces the `data/*.bin` blobs, the generated `asm/*.h` + `codehandler*.h` headers, and `libfatfs-ppc.a`.
- **arm** (`toolchain-devkitARM.cmake`, big-endian `arm-none-eabi-`): `fatfs-arm`, the `kernel` (→ `kernel.zip`), and `kernelboot`.
- **wii** (`toolchain-wii.cmake`, `powerpc-eabi-` + libogc): the `loader` GUI, embedding every data blob and converting to `boot.dol`.

Groups are wired **ppc → arm → wii** via `ExternalProject` `DEPENDS` and share three output dirs (`build/launcher/shared/{gen,data,lib}`). The root project drives the whole thing through an `ExternalProject_Add(nintendont_launcher)` that depends on the `mod_bins` target only to *package* the bins — no launcher source depends on the mod — and `scripts/package_launcher.py` produces `susamune_launcher.zip` (jinja2 `meta.xml` + `launcher/icon.png` + the bins).

**Toolchain sourcing** (was the old Git-Bash/`make` detour): `launcher/cmake/BundledToolchain.cmake` uses `DEVKITPPC`/`DEVKITARM` from the environment if set, otherwise extracts the bundled `launcher/nintendont_devkitpro_win32.zip` (a Git LFS file) and, on Windows, mirrors the `libwinpthread` DLL next to `cc1`. The devkitPro tools the bundle lacks are replaced from CMake: `scripts/bin2s.py` (data → object, via `launcher/cmake/Embed.cmake`), `scripts/bin2h.py` (blob → header), `scripts/elf2dol.py` (ELF → DOL), and `kernel.zip` is produced with `cmake -E tar --format=zip`. No `make`, Git Bash, or tool shims are involved anymore.

## Build & test loop

First-time setup: `python setup_venv.py` (creates `venv/` with the Python packages the build scripts need). Then:

```
cmake --preset dev_console              # configure (see CMakePresets.json for the rest)
cmake --build build                     # build build/mod_<vers>.bin for every VERS entry (default `mod_bins` target)
cmake --build build --target dol        # patch a main.dol from the source ISO (Dolphin dev)
cmake --build build --target emulator_patches # source-free BPS files for every VERS entry (IS_EMULATOR=ON)
cmake --build build --target iso        # rebuild build/susamune_<vers>.iso
cmake --build build --target launcher   # build the Nintendont HBC app zip (build/susamune_launcher.zip)
cmake --build build --target gecko      # emit build/susamune.txt (Dolphin cheat form; currently broken in-game)
```

**`VERS` is a list.** `-DVERS="jp;us;pal"` builds one mod object, manifest, `mod_<vers>.bin`, and source-free BPS per entry; that is what CI does for a release. The ISO/DOL pipeline can only target one disc at a time (one `SMS_ISO`, one `out_iso`), so `dol`/`iso`/`gecko` follow the **first** entry, `VERS_PRIMARY`. Each version gets its own `susamune_obj_<vers>` target because `SUSAMUNE_VERSION_*` selects a whole MEM1 layout.

`cmake -B build -G Ninja` works too; the presets just bake in Ninja, the build dir and the option set (`release_console`/`release_emu`/`dev_console`/`dev_emu`). The Visual Studio generator is rejected.

Pipeline: CMake compiles/partial-links `src/*.cpp` into `build/susamune_pre_<vers>.o` with the Kuribo clang fork, then `scripts/link_mod.py <mode>` links it against `maps/<vers>.ld` and emits one of three outputs from the same hook table:

- `launcher` → `build/susamune_manifest_<vers>.json` (base address, initialized image prefix, full runtime size, and the `(addr, word)` writes realizing every hook plus the arena reservation). `scripts/gen_mod_bin.py` packs each manifest into `build/mod_<vers>.bin` — the default `mod_bins` target — and the launcher packaging drops those into the app zip. **dol_c_kit's intermediates are named after `project_name` in a shared `obj_dir`, so `link_mod.py` suffixes it with the version**; without that the three parallel links clobber each other.
- `patch_dol` → a patched `main.dol` (the `dol` target; `iso` wraps it back into an ISO).
- `gecko` → a Gecko cheat list (the `gecko` target).

The compiler is forced before `project()` and its check skipped, so CMake never identifies it; `CMAKE_DEPFILE_FLAGS_CXX` is therefore set by hand in `CMakeLists.txt`. **Without it no depfile is written and editing a header rebuilds nothing** -- do not drop it. The build uses Kuribo's clang fork (`KURIBO_COMPILER_HOME`, defaulting to `toolchain/`) with `-Werror`, c++17, no exceptions/RTTI/standard library. **`-fsigned-char` is required**: `s8` in `include/` is a typedef for plain `char`, which is unsigned on this target, while the game structs it describes were compiled by CodeWarrior, where it is signed. Without it every negative `s8` reads back as `0..255`. The source ISO defaults to `<ISO_CODE>.iso` in the repo root (e.g. `GMSJ01.iso`); override with `-DSMS_ISO=<path>` or the `SMS_ISO` env var. The linker script is regenerated on demand with `cmake --build build --target regen_ld` after `maps/<vers>.map` changes.

Build options (toggle in `ccmake`/`cmake-gui`, or with `-D<name>=<value>`):

- `IS_EMULATOR` (default OFF) — ON targets Dolphin (`kSnapshotBase = 0x70000000`), OFF targets Wii/Nintendont (the dedicated `0x91F00000–0x92F00000` window). Sets the `IS_EMULATOR` compile define. **Test on Dolphin first** (`-DIS_EMULATOR=ON` + the `dol`/`iso` targets); for console builds, leave it OFF and keep all launcher MEM2 changes in `include/susamune/mem2_map.h`.
- `ENABLE_SAVESTATE_DBG` (default OFF) — compile the savestate status overlay and its debug strings/state.
- `ENABLE_MEM_DIAGNOSTICS` (default OFF) — compile the MEM1 root-floor/scratch-canary/stage-heap overlay used for console stress tests.
- `ENABLE_DEBUG_WARPS` (default OFF) — compile the debug-only `Warps` and `Stages` menu tabs and stage-warp implementation. When disabled, `debug_warp.cpp` is omitted from the target.
- `UPDATE_ISO_METADATA` (default OFF) — for the `iso` target, bump the game code (01→02), swap banner/name, etc.
- `VERS` (list of jp/us/pal, default `jp`) — game versions to build mod binaries and source-free BPS patches for. Each selects a map/linker script, patch addresses, game ID, and the C++ MEM1 layout definitions. The first entry is `VERS_PRIMARY` and drives the ISO/DOL targets; the launcher is version-agnostic.

## Decomp cross-reference

For any game-side type whose layout you need precisely, the canonical source is `../../src/sms` (the SMS decomp). The headers under `include/` are reverse-engineered approximations that are good enough to compile against, but if a field offset matters (e.g. the offset of `mGamePads` in `TApplication`, or the exact size of `TFlagManager`), confirm against the decomp.

## SD release deployment

Every completed pre-release or release must also be installed to the user's Wii
SD card when it is mounted at `D:`. Validate that `D:\Apps\moonshine_launcher`
is the existing Moonshine app before writing, copy only the files carried by the
verified final launcher ZIP, and preserve unrelated files such as `theme/`.
After copying, compare every installed file against the package and confirm the
version in `meta.xml`. If the expected SD layout is not mounted, report that
instead of guessing another destination.
