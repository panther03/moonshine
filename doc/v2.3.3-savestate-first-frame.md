# Savestate first-frame rendering repair

## Cause and scope

Retail `TMarDirector::direct` pipelines its drawing: the next call can first
consume the queues prepared by the preceding call. A snapshot includes those
prepared retail queues. `GhostModel::onSavestateLoaded` cleared Mario's opaque
and translucent queues after restore, leaving the separately submitted ground
shadow visible until the next ordinary update repopulated Mario's queues.

The feedback-5 PAL image reproduces the user's exact shadow-only frame in
`build/v2.3.3-feedback6/load-frame/baseline/framedump_3733.png`; Mario returns
in frame 3734. A private same-state experiment replacing only the retirement
call shows Mario and FLUDD in the first restored frame, 8656. This diagnostic
establishes the cause; simply removing retirement is not the production fix.
The labeled comparison and all source-frame hashes are in that directory's
`diagnostic-contact.png` and `diagnosis.json`.

## Production change

The existing post-GX-barrier cleanup still retires Mario's A/B queues. It then
selects those two queues temporarily and calls only retail FLUDD `ENTRY` and
Mario `entryModels`, using the restored matrices. The prior J3DSys queue
selectors are restored before returning. The native visible, performing and
ENTRY-suppression gates are retained, including a hidden Ghost Watch observer.
The legacy Mario declaration is corrected to two halfwords at `0x114/0x116`;
visibility belongs to the first halfword. The former combined word made the
new gate read byte `0x117` instead of `0x115` on PowerPC. Object size and the
following attribute-word offset are unchanged.

This does not call Mario `perform`, MOVE, CALC_ANIM, view calculation, dirt,
damage-fog, shadow submission or tremble movement. The audited ENTRY callees
do not consume the graphics argument. Mario's body, hands, cap and cart use
the cleared player queues. Yoshi's separate queues remain intact. A ridden
Blooper is already in the restored object-light queue, so its status branch
is suppressed only around `entryModels`; the exact original status word is
restored immediately afterward. This avoids submitting that packet twice.

Sharing the existing runner-slot lookup and prepared-packet reset compensates
for the repair's code size. No memory reservation or state capacity grows.
There are no codec, file, ordinary timer or lifecycle-barrier changes.

The change does not rebuild or clear shared environment-light queues. The
audit also identified pre-existing references to excluded private ghost
packets in those queues; handling their lifetime across restore is a separate
issue, and this repair must not be described as resolving it.

## Validation scope

The actual production helper is executed by the host render-binding fixture
for fourteen scenarios, covering missing owners/buffers, native hiding,
perform suppression, FLUDD presence, unrelated flags, surf/cart status and
restoration of queue selectors. The fixture derives the flag field types from
the production header and includes the observed big-endian visibility bytes
`04 12 00 00`, as well as an opposite-bit adjacent halfword. Existing
render-lifetime and restore-binding
checks remain in force. Final emulator evidence is kept separately in
`build/v2.3.3-feedback6/final-load-frame`.

The user's corrected prior Wii measurement is 0.300 seconds until visible
Mario, versus 0.334 seconds on the preceding build. Recovering the missing
presentation frame could make visible recovery coincide with their 0.267-
second first-restored-frame measurement. That remains a hardware expectation,
not a new measured Wii result or a faster-decoder claim. Further level-load
potential is assessed in `v2.3.3-feedback6-load-feasibility.md`.
