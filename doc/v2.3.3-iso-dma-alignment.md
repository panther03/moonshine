# ISO cache DMA alignment

Short ISO reads could leave the cache ring's next destination unaligned. Both
storage backends check 32-byte destination alignment: SD then reads through its
64 KiB temporary buffer and copies the result, while USB uses its 16 KiB transfer
buffer. This unnecessary copy persisted after the previous sector-alignment
improvement, because sector alignment of the disc offset does not imply alignment
of the destination in memory.

`ISORead` now rounds the next allocation start up to 32 bytes before checking the
existing ring bound. The gap remains unused; it is never read from disc or
included in a cache entry. Wrapping and overlap invalidation retain their existing
rules. There is no larger memory reservation, additional cache, change to file
formats, transfer-size increase, or change to timer code. The ARM object adds 16
bytes of text and no data/BSS; PPC staging is unaffected.

## Evidence

The existing real PAL DVD trace contains 3,126 requests. The before/after test
executes the actual `ISORead` code, then the full production FatFS reader against
the user's PAL ISO bytes. Cache destination offsets are preserved when presenting
each read to FatFS. The six modeled layouts cover contiguous and 16-extent files
with 4, 32 and 64 KiB clusters.

| Work across the complete trace | Before | After |
| --- | ---: | ---: |
| Cache fills | 894 | 894 |
| Fills with an unaligned destination | 374 | 0 |
| Device read commands | 1,725 | 1,725 |
| ISO bytes requested | 38,993,004 | 38,993,004 |
| Direct-output device reads requiring a bounce copy | 451 | 0 |
| Direct-output bytes requiring a bounce copy | 17,732,608 | 0 |

Every returned byte matches the ISO and before/after digests match. Guard bytes
remain intact, no read crosses a noncontiguous extent, writes remain zero and
the largest device request remains 64 KiB. Internal FatFS sector-buffer transfers
are excluded from the bounce-copy totals because their production alignment is
independent of the cache allocation.

These are source-based work counts, **not an emulator or Wii elapsed-time
measurement**. They do not predict a specific load-time reduction. The user's
earlier Sirena 4 timings compared 2.3.2 with build `9F8C6CD1` and predate this fix.

29 focused ISO-cache, FatFS and read-speed tests pass. New cases cover an odd-size
fill followed by a direct-aligned fill, padding at the ring boundary, preservation
of adjacent entries, and randomized overlap/wrap reads with odd lengths. The ARM
before/after object builds complete without warnings.
