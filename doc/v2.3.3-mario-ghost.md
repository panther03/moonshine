# Regular Mario ghost in V2.3.3

The third appearance reuses an existing model heap. It adds no heap, asset-vault
reservation, ghost-file payload or savestate storage. This supersedes the direct
load limitation documented in `v2.3.2-mario-ghost-feasibility.md`.

## Selection and ownership

The existing appearance setting keeps `0 = Shadow Mario` and `1 = Piantissimo`;
`2 = Mario` is appended. There remain two physical model slots. Mario replaces
Piantissimo in the second slot while selected; the other runner uses Shadow
Mario. It does not mean three simultaneous runners.

`/mario/bmd/ma_mdl1.bmd` already belongs to the loaded retail Mario archive.
The ghost shares its immutable geometry and original texture pixels, plus the
existing animation resources. Joints, shapes, materials, transforms, display
lists and animation calculator are private. The renderer temporarily changes
the borrowed animation frame only around its own calculation and restores it.
The live Mario's materials are not edited. User recolours are not automatically
copied to the ghost, and the ghost file does not store model assets or colours.

The asset is 117,248 bytes in JP, US and PAL; all three original ISOs produced
SHA-256 `33ae21b047a8dff0d76fed843dbcf1accfd85b6b427367dd23e6465ac2574eb6`.
The first 76,000 bytes have CRC32 `0A21E8B8`. This checked prefix includes all
allocation-driving sections but excludes the texture image headers that retail
pollution rendering may replace in place. The ghost never rewrites those headers.

## Making the model fit

Retail Mario has eleven five-stage materials. Their large TEV blocks cause the
normal model constructor to allocate oversized double display lists. Before
constructing the private model, the ghost replaces each private material's TEV
block with a compact three-stage block. A clean base texture replaces the first
three pollution-compositing stages; the original lighting-lookup and specular
stages remain. Both RGB lighting channels, the original texture-coordinate
generators, and native TEV/konst colours are retained. Opacity travels separately
through alpha. The optional Aloha-shirt shape is hidden; the embedded ordinary
cap and hands stay visible.

The earlier one-stage texture-times-diffuse conversion was visibly wrong: it
omitted Mario's native lighting lookup, creating a dark band across the cap and
body. Keeping diffuse channel flags and binding a stage light alone did not
restore that missing material pipeline. See the controlled same-pose comparison
in `v2.3.3-ghost-lighting-animation.md`.

The old TEV blocks remain allocated but unused. The allocation
budget includes them; it does not depend on freeing objects through an uncertain
retail ABI. Material conversion changes only checked private heap addresses.

Production preflight still requires 87,040 usable bytes before loading, and the
final usage is checked before publication. The current three-stage measurement
comes from the US diagnostic `D499B9F9`, using the same 90,112-byte heap size; the
older diagnostic evidence below predates this shading correction. Reservations
and model/ghost file formats are unchanged.

Changing between Mario and Piantissimo in the same stage uses the existing
stage-generation retirement path: rendering quiesces, `GXDrawDone` completes,
player packet lists retire, attachments clear, then the alternative slot is
rebuilt. Settings restored in the same stage use this same path. Existing
savestate packet cleanup remains in place. No reservation or wire setting ID moves.

## Verification and limits

Focused host tests execute the material conversion and check TEV colour/alpha
math, private buffer boundaries, two-slot roles, unchanged old choice tables,
and ARM INI round trips for all three appearance values and regions.

Runtime investigation exposed an existing standalone Dolphin limitation:
GPU-consumed body matrices and display lists live in the fake MEM2 address range.
Retail GX address masking does not make that range GPU-accessible. The old
Piantissimo body could be invisible and, at full opacity, obscure live Mario.
Water and FLUDD attachments were not the cause. This is distinct from the Wii's
real MEM2 mapping; no Wii or Wii U result was obtained from this investigation.

To test the new model separately, a private US diagnostic placed one body in
90,112 bytes of the already reserved 128 KiB MEM1 attachment area. It disabled
the Shadow slot and attachments. No production reservation grew and this
diagnostic allocation is not a production change.

That fixture verified the front-facing Mario palette, cap emblem, eyes, hands,
and shoes; all four opacity choices; and rebuilding Mario in the same stage.
Live Mario stayed visible, and its material objects were byte-identical across
opacity and appearance changes. The model used 71,244 bytes before and after
reload. Piantissimo's stage resource was absent in the Bianco test; that switch
was an unavailable-resource/recovery check, not a Piantissimo visual test.

This does **not** establish complete production Dolphin rendering, simultaneous
two-ghost rendering, Mario with all attachments, or Wii/Wii U runtime behavior.
The standalone Dolphin fake-MEM2 limitation still needs its own fix.

Local evidence is kept under `build/v2.3.3-mario-prototype`: `allocation_audit.json`,
`verify_regions.json`, `mem1-fixture/verification.json`, and
`runtime/mario-runtime-proof.json` with named screenshot hashes. The private ISO
CRC32 was `6B382E2F`; its source/fixture hashes and exact diagnostic scope are in
the receipt. These are private test artifacts, not release payloads.
