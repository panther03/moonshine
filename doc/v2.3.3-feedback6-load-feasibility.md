# Feedback 6: remaining load-time potential

This is a read-only feasibility audit. No additional performance patch or
benchmark was made for this report.

The initially reported 0.267-second loads 1/2 end on a restored frame where
Mario's shadow is present but his model is absent. They are **not** comparable
to the preceding 0.334-second visible-Mario measurements. The user corrected
that endpoint to 0.300 seconds. Slot 3's reported 0.467 seconds uses the first
restored-frame endpoint; its first-visible-Mario endpoint was not separately
confirmed. Do not infer a corrected slot-3 value.

The one-frame rendering defect is separate from checksum/decode cost. Making
that restored frame draw Mario correctly could advance visible recovery
without making the decoder itself faster. It must not be counted as another
measured checksum improvement. The prior controlled emulator results and
their different measurement scope are documented in
`v2.3.3-savestate-lifecycle-feedback5.md` and
`v2.3.3-state-checksum-speed.md`.

## What remains during ordinary level loading

The latest hardware level timings show no clear gain beyond roughly one
rendered frame. They do not establish the share spent in storage, decompression,
construction or presentation, nor establish that the small differences are
repeatable. Further ISO-cache tuning has no demonstrated large remaining win.

The local decomp identifies these useful profiling boundaries:

| Phase | Exact source or hook target | What to distinguish |
| --- | --- | --- |
| Teardown | `System/Application.cpp:552` and `:567` | Director destruction and stage-heap `freeAll` |
| Resource worker | `System/MarDirector.cpp:61`; `TMarDirector::loadResource`, PAL `0x802AD3D8` | Worker start/end versus actual DVD waits |
| Archive reads/decompression | `System/Application.cpp:106`; `SMSLoadArchive`, PAL `0x8029FAB8` | Compressed `.szs` path versus raw archive reads |
| Stage archive | `System/Application.cpp:793`; `TApplication::mountStageArchive`, PAL `0x8029D858` | Selected scenario's resource cost |
| Main-thread construction | `System/MarDirectorDirect.cpp:47–55`; `TMarDirector::setupObjects`, PAL `0x802AF6C4` | Resource-worker completion versus object construction |
| Moonshine setup | `src/main.cpp`, `onSetup` | Existing setup-enter, retail-setup-return and stage-ready markers |
| Transition/presentation | `System/MarDirectorDirect.cpp:433`, `:465`, `:693` | Audio readiness, fade completion and first actionable/visible frame |

`System/...` paths above are relative to
`build/research/sms-decomp/src`. The corresponding retail function addresses
are in `maps/pal.ld`. These decomp units are marked non-matching, so their
source is a profiling guide rather than timing evidence or permission to
remove a wait without checking the retail binary.

The resource path reloads common particle, Yoshi and parameter archives as
well as the scenario archive; `SMSLoadArchive` tries compressed input first.
Afterward, setup constructs objects and runs `loadAfter`. Cached disc bytes
alone do not avoid decompression or this reconstruction. The retail path also
contains 0.4-second wipes, but their overlap and the existing Intro Skip hooks
mean that 0.4 seconds cannot simply be subtracted from the measured load.

## Defensible expectation

A few additional frames remain plausible, but no amount is proved by this
audit. There is no current evidence that another small storage patch can halve
these loads. A larger improvement would likely need avoiding repeated
decompression or reconstruction. Keeping decompressed resources resident
would require explicitly budgeted lifetime/storage, since the stage heap is
cleared; it cannot safely reuse old heap pointers or silently borrow savestate
capacity. An SD cache would trade decompression against larger reads and also
needs measurement.

The next useful experiment is one timestamp breakdown across the phases above,
using the same Sirena transitions and identical visible-frame endpoints.
It should establish the dominant phase before choosing further code changes.
