# V2.2.0 size, MEM1/MEM2, launcher, and kernel audit

Release source baseline: the local Moonshine V2.1.1 "Hot Streak" release state.

The pristine binary controls captured before that local update remain tag
`v2.1.0`, commit `353cafea6268b08fb1fb01ff1f6523ba37165c94`.
Measurements against those artifacts are labelled V2.1.0 below; they are not
being relabelled as V2.1.1 results.

This records the measurements, accepted changes, rejected candidates, and
implementation order for the V2.2 optimization pass.

## Hard guardrails

- Timer code was not changed. `qft_timer`, QF display/timing behavior, split
  timing semantics, timer settings/hooks, and timer files are excluded from all
  optimization candidates.
- `SplitStats::Runtime`/`sStateStorage` is measured because it dominates BSS,
  but moving, packing, or otherwise changing it is prohibited: it contains
  timer/split state.
- The MEM1 arena, mod region, and scratch address must not be shrunk or moved in
  this work. Although the reservation has visible slack, shrinking it moves the
  scratch tail and could alter timer behavior. This is therefore not a
  candidate.
- The permanent ARM split-statistics migration buffers are also excluded. They
  are split-state code even though they are not part of the PPC timer source.
- Launcher/kernel figures are region-neutral. One launcher serves JP, US, and
  PAL; only the injected PPC blob differs by region.

## Audit passes performed

The repository was checked independently from twelve directions rather than
using the single flat-binary size as a proxy for everything:

1. clean/tagged source and build-configuration baseline;
2. ELF alloc-section classification for JP, US, and PAL;
3. initialized-span, BSS-tail, and alignment-gap accounting;
4. largest symbols and fixed tables;
5. translation-unit and largest-function text attribution;
6. final linker flags and dead-section behavior;
7. manifest and `mod_<region>.bin` format/loader validation;
8. MEM1 reservation, working cap, attachment heap, and scratch layout;
9. the complete console MEM2 address map and lifetime overlays;
10. the 64 KiB ARM/PPC configuration ABI and its explicit gaps;
11. launcher embedded assets and persistent heap allocations; and
12. kernel sections, BSS pools, fixed linker gaps, and compression feasibility.

### Implemented: bounded UTF-8/UTF-16 FatFS paths

The FatFS wrapper no longer routes paths through the locale-dependent
`mbstowcs`/`wcstombs` pair or a 32-bit `wchar_t` intermediate. It now performs
bounded UTF-8 to UTF-16 conversion directly, including real surrogate pairs
for supplementary Unicode. Malformed continuations, truncation, overlong
forms, UTF-8-encoded surrogates, values above `U+10FFFF`, and path-buffer
overflow fail as `FR_INVALID_NAME` instead of being truncated. Directory names
combine valid UTF-16 pairs, replace an isolated corrupt-media surrogate with
`U+FFFD`, stop only at a complete scalar when the output fills, and remain
NUL-terminated.

The shared scratch union is 1,024 bytes: 512 UTF-16 path units or 766 UTF-8
name bytes. The latter is exactly enough for FatFS's 255-unit LFN maximum in
the worst three-byte-per-unit case plus the terminator. The old PPC buffers
occupied 2,560 bytes, so PPC BSS falls by exactly 1,536 bytes. The loader must
no longer initialize a process locale: GRRLIB now validates and decodes UTF-8
scalars directly with the same strict decoder, and passes each scalar straight
to FreeType. This also removes the old temporary `wchar_t` allocation from
every draw and width query; the previous allocation requested four times the
UTF-8 byte count plus four bytes on each call.

The ARM kernel has no other multibyte/wide-character consumer. Its map
attributes the cross-built change exactly:

### Implemented: chunked IPL-font transfer

The launcher formerly allocated one aligned `0x50000`-byte buffer, read the
complete console IPL font into it, copied it to the fixed MEM2 font window, and
freed it. EXI DMA requires a MEM1 destination, but it does not require the
entire font to be resident in MEM1 at once. `LoadIplFonts` now reads through one
256-byte, 32-byte-aligned stack chunk and copies each completed chunk directly
to the same MEM2 alias before invalidating the unchanged final range.

In the current `-Os` object, the out-of-line helper is `0x6c` bytes and has a
328-byte stack frame; keeping it out of line restores `main` to its measured
10,576-byte Moonshine frame. The exact heap payload removed is 327,680 bytes. At the
transfer's peak the replacement stack frame is 328 bytes, so simultaneous
stack-plus-heap demand falls by **327,352 bytes**, excluding allocator metadata.
The loop covers exactly `0x50000` bytes with no remainder and preserves the
original ROM offset, MEM2 destination, and cache range. Focused source tests
lock those bounds and the alignment contract; Wii/vWii boot remains the
hardware gate.

### Implemented: normal GameCube IPL DIMM overlay

The optional normal IPL formerly requested a 2,097,152-byte MEM1 heap buffer.
Normal GameCube IPL and Triforce boot are mutually exclusive, so the loader now
stages that payload in the first 2 MiB of the existing 3 MiB DIMM reservation
only on the non-Triforce path. This moves the bytes rather than reducing total
reserved memory, but removes the full payload plus allocator overhead from the
launcher's peak MEM1 heap demand.

The ARM kernel starts after the PPC has staged the IPL, and `DIinit(true)`
normally clears DIMM. A private handoff bit is therefore cleared before every
probe and set only after a successful, exact-size read. The ARM preserves DIMM
only when that bit is present; skipped IPL, Triforce, missing-file, short-read,
and I/O-error paths still clear the whole buffer. This ordering is covered by a
source contract and the combined ARM/PPC cross-build. Hardware testing must
still exercise both a normal 2 MiB IPL and Triforce/SegaBoot.

### Implemented: factored IPL patch tables

The legacy GameCube IPL patcher repeated the same English-language, PAL
animation, video-filter, and boot-jingle writes across revision branches. It
now keeps the four language layouts and two PAL animation layouts in compact
constant tables and applies the seven filter and seven jingle sites through
shared helpers. The branch probes and every write's final address, value, and
ordering are unchanged.

Against an isolated current-source `-Os` control, the allocated `ipl.c` object
falls from 2,304 to 1,848 bytes: **456 bytes removed**. The end-state oracle
covers all four language layouts, both PAL animation layouts, every
progressive/sharp combination at all seven filter sites, and all seven jingle
calls. The compact result retains 1,084 bytes in `load_ipl`, 272 in the
descrambler, 268 across the four helpers, 60 in the BS2 video table, and 164
bytes of new compact patch data. Hardware IPL revision/progressive-mode smoke
testing remains the release gate.

### Implemented: table-driven Triforce detection and bounded loader paths

`TRISetupGames` formerly duplicated the same DOL read, signature comparison,
logging, device-path formatting, and save creation across 15 branches. The
ordered `TriforceGames` table now holds every original DOL offset, exact log
label, save/settings filename, file size, and F-Zero AX two-file action. One
loop retains first-match behavior for files, extracted FST games, real discs,
and Wii VC.

Against the frozen O3 object, `TRISetupGames` code falls from 4,084 to 1,200
bytes. Read-only strings/table data rise from 1,049 to 1,228 bytes, for a net
5,133 to 2,428 allocated bytes: **2,705 bytes removed**. Reusing one bounded
image/FST path buffer also reduces its stack frame from 4,744 to 4,504 bytes,
**240 bytes less**, while short reads, failed Wii VC disc opens, and truncated
paths now fail closed.

The live Moonshine mod path now uses one bounded format pass instead of a
separate 32-byte name buffer and second format call. Its O3 object falls from
1,211 to 1,185 allocated bytes and its stack frame from 8,344 to 8,320 bytes.
The dormant title database no longer writes a 741st row or splits an overlong
line into false titles; title, MD5, update, mod, image, extracted-FST, and
Triforce save paths all reject `snprintf` truncation. The title/MD5/update
modules are currently garbage-collected in full, so their hardening has no DOL
cost. `scripts/test_loader_path_safety.py` locks all 15 actions, worst-case save
paths, Wii VC short-read cleanup, title capacity, exact 63/64-byte line
boundaries, CRLF, and unterminated final lines.

The broader legacy updater is intentionally not resurrected in this pass. This
fork has neither its upstream `http.c` implementation nor a live
`UpdateNintendont` caller. Upstream `http_get_result` publishes a null content
pointer on failure but returns true, while `update.c` dereferences that pointer;
the exhausted-retry path even passes null output pointers to an implementation
that writes through them on failure. Successful response buffers also have no
guaranteed NUL for the version `sscanf`, and allocation/write results are not
fully checked. Because the whole feature is linker-collected, fixing only one
side would add no release value. Restore the HTTP implementation and harden the
pair under a bounded-response oracle before exposing updates again.

### Implemented: fixed storage for the savestate controller

`SavestateManager` is persistent for the life of the game and was never
destroyed, but it was allocated from Sunshine's nearly full system heap during
stage setup. It is now placement-constructed once in aligned mod BSS. A
`static_assert` fixes the controller at 56 bytes, so this returns exactly 56
payload bytes plus allocator metadata to the game heap. The mod's arena
reservation already covers its complete BSS and is unchanged, so this is heap
headroom rather than a new reservation or a claim of lower total MEM1.

## Where the PPC bytes are

### BSS

`sStateStorage` in `split_stats.cpp` is 28,304 bytes (`0x6E90`). It accounts
for 92.7% of JP BSS and 94.3% of US/PAL BSS. It is intentionally excluded from
optimization because it is timer/split state.

The remaining BSS is only 1,721 bytes in US/PAL. JP had one additional
512-byte `sFontSafeText` buffer. The current V2.2 branch has already moved that
JP-only scratch buffer into a bounded, cache-line-aligned unused MEM2 gap at
`0x92EF5940-0x92EF5B40`. Expected result: exactly 512 fewer JP BSS/MEM1 bytes,
with no US/PAL change and no increase in the MEM2 reservation. A post-change
three-region build is still required to confirm the final map.

## Implemented V2 mod format: do not serialize BSS

The current `scripts/dol_c_kit/devkit_tools.py::__process_project()` writes
every `SHF_ALLOC` section. Pyelftools returns zero bytes for `SHT_NOBITS`, so
the generated flat binary physically carries the complete BSS tail as zeros.
GNU `objcopy -O binary` confirmed that an ordinary binary stops at the last
initialized byte instead.

The initialized prefix should be padded to the BSS start/alignment, while the
runtime image size remains unchanged:

| Region | Initialized file prefix | Runtime image | BSS tail omitted | New packed file |
|---|---:|---:|---:|---:|
| JP | 270,424 (`0x42058`) | 301,064 | 30,640 (`0x77B0`) | 270,632 (`0x42128`) |
| US | 269,736 (`0x41DA8`) | 299,880 | 30,144 (`0x75C0`) | 269,944 (`0x41E78`) |
| PAL | 269,876 (`0x41E34`) | 300,008 | 30,132 (`0x75B4`) | 270,084 (`0x41F04`) |

Exact release-package and SD-read saving across the three files: 90,916 bytes.
This does **not** reclaim runtime MEM1; it removes redundant zeros from the
file and staging I/O.

The V2 format is now implemented as follows:

1. `SUSAMUNE_MOD_VERSION` is 2.
2. The unchanged 32-byte header stores initialized `codeSize` and full runtime
   `memSize`; disk size is computed as
   `header + codeSize + writeCount * 8`.
3. The launcher manifest stops after the final initialized `SHF_ALLOC` byte,
   retaining address gaps and word padding. DOL and Gecko modes still receive
   the legacy full image.
4. `PatchSusamune` copies `codeSize`, zeros
   `[base + codeSize, base + memSize)`, and cache-syncs the complete `memSize`
   range before installing hooks. This repeats on every in-session reset.
5. Loader, kernel, and crash-report validation use overflow-safe checks:
   `codeSize <= memSize <= working cap`, both sizes aligned as required, write
   count bounded by the staged file length, exact computed file length, valid
   base/game/version, and unchanged arena reserve.
6. Asset-vault availability compares against computed on-disk size, not
   `memSize`.

The existing post-menu JP object independently proved the path without a new
compile: runtime size 301,608, initialized prefix 270,960, omitted tail 30,648;
the complete omitted tail contained only zero bytes. Its synthetic V2 packed
file was 271,168 bytes versus 301,816 for V1. The exact 90,916-byte three-file
baseline saving still needs the fresh JP/US/PAL build because the current
branch also changes JP BSS.

Likely files are `include/susamune/mod_bin.h`,
`scripts/dol_c_kit/devkit_tools.py`, `scripts/gen_mod_bin.py`,
`launcher/loader/source/SusamuneMod.c`, `launcher/kernel/Patch.c`, and their
format/negative tests. This changes startup representation only; runtime
addresses, timer state addresses, scratch, and arena layout remain identical.

A second-stage compression experiment is promising but lower priority. On the
three initialized prefixes, Python zlib level 9 produced 142,128, 141,868, and
141,760 bytes. The ARM kernel already contains a PRS decompressor, but a new
compressed header, bounded decompression, checksum, reset behavior, and a
matching build-time compressor would all need validation. BSS elision gets a
clean win without that complexity.

## MEM1 ledger

| Range/quantity | Bytes | Status |
|---|---:|---|
| working cap | `0x50000` = 327,680 | flat PPC image must fit |
| attachment heap | `0x20000` = 131,072 | begins at offset `0x50000` |
| unassigned tail before scratch | `0xFFC0` = 65,472 | not actionable under timer/scratch guardrail |
| scratch | `0x40` = 64 | address must remain unchanged |
| complete mod region | `0x80000` = 524,288 | fixed for this work |
| retail debug-stack gap | `0x2000` = 8,192 | required by arena derivation |
| root-heap displacement | `0x82000` = 532,480 | fixed for this work |

The attachment heap is already nearly exact: two `0xFF00` instance bounds plus
`0x130` fixed exp-heap overhead require `0x1FF30`; after 32-byte alignment only
192 bytes are safely spare. It is not worth tightening.

Although the code image has about 26-28 KiB headroom and the tail has 65,472
unassigned bytes, neither produces a safe heap win without changing the arena
or scratch layout. No arena/cap/scratch patch is proposed.

## Console MEM2 ledger

`0x91000000-0x93000000` is completely tiled. There is no unowned block between
the current reservations.

| Range | Purpose | Bytes |
|---|---|---:|
| `0x91000000-0x91300000` | disc cache / RealDI | 3,145,728 (`0x300000`) |
| `0x91300000-0x91400000` | SegaBoot | 1,048,576 (`0x100000`) |
| `0x91400000-0x91700000` | Triforce DIMM | 3,145,728 (`0x300000`) |
| `0x91700000-0x91780000` | DI scratch | 524,288 (`0x80000`) |
| `0x91780000-0x91900000` | loader disc buffer, then three ghost slots | 1,572,864 (`0x180000`) |
| `0x91900000-0x91E7F000` | generic file-patch handoff | 5,763,072 (`0x57F000`) |
| `0x91E7F000-0x91F00000` | staged mod plus model vault | 528,384 (`0x81000`) |
| `0x91F00000-0x92EF0000` | snapshot payload | 16,711,680 (`0xFF0000`) |
| `0x92EF0000-0x92F00000` | config/runtime ABI | 65,536 (`0x10000`) |
| `0x92F00000-0x93000000` | ARM kernel | 1,048,576 (`0x100000`) |

Important lifetime facts:

- The 1.5 MiB loader disc buffer is not an additional runtime reservation. It
  becomes three exact 512 KiB ghost slots after handoff.
- The mod-staging window is logically full: `0x5F000` reset-safe file prefix
  plus a `0x22000` immutable model vault equals `0x81000` exactly.
- The pristine largest staged file is 301,272 bytes, leaving 87,848 bytes to
  the current `0x5F000` ceiling. After BSS elision the JP file would leave
  118,488 bytes. If the loader enforces a separate `0x4A000` staged-file cap,
  the fixed tail `0x4A000-0x5F000` becomes 86,016 bytes of reusable runtime
  capacity while retaining 32,472 bytes of JP file-growth room. This is usable
  for future RNG trace/metadata buffers, but it does not increase total MEM2
  and must be reset/reinitialized without corrupting the immutable staged file.
- Ghost playback has only 544 bytes before its segment table; transfer has a
  32-byte boundary gap. The record-side catalog region has 17,440 bytes of
  shape-dependent tail, not a generally free slot. Do not shrink the three
  ghost slots without redesigning the shared loader-buffer lifetime.
- The snapshot reservation must not be reduced based on a single stage. Its
  high-water mark needs instrumentation across all regions, large stages, and
  transitions before any reduction can be considered.

### Configuration/runtime block

The 64 KiB config block has 14,144 bytes (`0x3740`) explicitly unassigned in
the V2.1 map, principally `0x5940-0x8800` (11,968 bytes). The JP font scratch
now consumes `0x200`, leaving 13,632 bytes (`0x3540`) explicitly unassigned and
`0x5B40-0x8800` as the principal 11,456-byte gap.

It cannot simply be shortened: the split-statistics mailbox pins
`0x8800-0xF800` and the live PB mirror pins `0xF800-0x10000`. These are shared
ARM/PPC ABI addresses. Use the internal gaps for small new state before adding
another MEM2 reservation.

### Implemented: omit unused loader unwind metadata from the DOL

The cross-built loader ELF still carries 54,876 bytes of allocatable metadata:
`.eh_frame_hdr` is `0x1B3C` bytes and `.eh_frame` is `0xBB20`. The old
`elf2dol.py` copied whole `PT_LOAD` segments, so both were present in the DOL
despite the loader being C-only. The linked image has no `_Unwind_*`, frame
registration, personality, C++ catch/throw, or backtrace consumer. Libogc's
similarly named `__exception_*` functions handle CPU exceptions and do not read
DWARF unwind tables.

The converter now emits allocated `PROGBITS`/`NOBITS` sections at their original
addresses, omits only the exact `.eh_frame` and `.eh_frame_hdr` names, and
refuses the conversion if a conventional unwind consumer appears or the ELF
has no symbol table with which to audit it. It also fails closed on unsupported
allocated section types, misalignment, overlap, and DOL section-count overflow.
Exactly adjacent retained sections are merged without changing bytes.

On the audited ELF, `boot.dol` changed from 1,480,512 (`0x169740`) to 1,425,632
bytes (`0x15C0E0`), a 54,880-byte (`0xD660`) saving. The four-byte difference
from the raw metadata total comes from repacking the retained ranges to the
DOL's 32-byte file alignment. Entry point `0x80004000` and BSS
`0x8016D640+0x81D00` are unchanged. Ten retained initialized sections totaling
1,425,316 bytes were compared byte-for-byte against both the ELF and old DOL;
11 host tests cover the success and fail-closed contracts.

The compiler still uses `-fno-unwind-tables`,
`-fno-asynchronous-unwind-tables`, `-ffunction-sections`, and
`-fdata-sections`, with linker `--gc-sections`, to avoid producing new local
waste and remove unreachable functions/data before conversion. PNG `setjmp`
error paths do not use DWARF unwinding, but startup and PNG-error behavior remain
hardware regression gates.

The loader now defaults to `-Os`, with `-O3` retained as a build-time escape
hatch. A controlled pair used identical source, generated files, embedded
archives, build timestamp, and toolchains. `-Os` changed `boot.dol` from
1,163,552 to 1,128,224 bytes (**-35,328**), `.text` from 717,728 to 683,072
(**-34,656**), `.rodata` from 430,808 to 430,144 (-664), and the static MEM1
span by **-35,008** bytes. Data, SBSS, and BSS were unchanged. Repeated clean
builds were byte-identical, every global data/BSS symbol retained its size and
relative layout, and the same ten ELF sections passed the independent DOL
verifier. `doc/v2.2.0-loader-optimization.md` records the hashes and ABI audit.

The final live-source artifact size and hash are recorded in the authoritative
clean-build section above. Wii/vWii boot, interactive UI, storage scan,
PNG-error, and ISO-read latency remain the release gate; any material latency
regression can use the existing `-O3` override.

### Implemented: reuse the kernel crash-probe buffer

### Implemented: overlay serialized ghost-catalog workspaces

## Explicitly rejected or deferred

- **Timer/split storage relocation:** prohibited, including the 28,304-byte PPC
  `sStateStorage` and 32,552 bytes of ARM split-migration temporaries.
- **Arena/mod-region/scratch shrinking:** prohibited because it would move or
  expose timer scratch/state even though `0xFFC0` is visibly unassigned.
- **Attachment-heap tightening:** at most 192 alignment-safe bytes.
- **Generic section reordering:** only 24-27 initialized address-gap bytes.
- **Ghost-slot shrinking:** the slots are loader-lifetime overlays with tight
  internal end structures, not three independent allocations.
- **Snapshot-window shrinking:** no stage/region high-water evidence supports
  it.
- **Release compression before BSS elision:** possible, but it adds a decoder
  protocol and failure mode to obtain a saving that zero elision gets first
  with much less risk.
- **Debug-info stripping as a DOL optimization:** debug sections inflate the
  intermediate ELF, but ELF-to-DOL already omits them.
