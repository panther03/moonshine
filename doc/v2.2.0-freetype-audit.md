# V2.2.0 launcher FreeType audit

## Result

The launcher now registers only the modules needed to open and render its one
embedded Unicode TrueType face. This reduces the cross-built `boot.dol` by
**255,456 bytes** with no change to the launcher BSS.

The final in-flight closeout also removes FreeType 2.4.12's deprecated
unpatented TrueType bytecode interpreter. The embedded font never selects that
interpreter, and an exhaustive cross-configuration oracle found no rendering
difference. Rebuilding only `truetype.o` reduces the current `boot.dol` by a
further **23,040 bytes**, again with no data or BSS change.

`SusamuneFreeType.c` still selects the small module closure from the vendored
archive, and the stock initializer remains selectable with
`-DSUSAMUNE_MINIMAL_FREETYPE=OFF`. The SFNT parser, auto-hinter, and rasterizers
remain byte-for-byte the original archive members.

## Provenance

The archive is FreeType **2.4.12**. Its source is tag `VER-2-4-12`, commit
`cecf93ef90c660a8b0b45e5adbbfb5ea443fb6b9`. The original archive was
`AD92989C0BD1A9BFF7AFDDAB209FF2808BDAEE897788CDC64BB5092B71079B8E`.
The final archive is deliberately a one-member rebuild:

- public headers report 2.4.12;
- 41 members remain byte-for-byte from the original devkitPPC release 26,
  GCC 4.6.3 archive;
- `truetype.o` was rebuilt from the source above with the bundled devkitPPC
  release 35 GCC 8.3.0, `-Os -mcpu=750 -meabi -mhard-float
  -ffunction-sections -fdata-sections -fno-unwind-tables
  -fno-asynchronous-unwind-tables`, and no debug sections;
- rebuilt `truetype.o` is 30,112 bytes, SHA-256
  `79EAE2A719487FD890AC4D614BC635377D6204E42705E50AA9D8F42BF1882484`;
- archive SHA-256 is
  `250649849EA117286D8A8F4D64448DB403D6C0C74297E637CE3E48BC7832678C`;
- its configuration disables both the patented bytecode interpreter and the
  deprecated `TT_CONFIG_OPTION_UNPATENTED_HINTING`; and
- its generated `ftmodule.h` registers the normal 2.4.12 driver set.

The repository originally contained the installed headers and binary archive,
but not the library source or build recipe. Reproducing the one rebuilt member
therefore starts from the pinned upstream source above; normal release builds
consume only the committed archive and in-tree initializer.

## Module closure

The ON build retains these seven archive members:

| Object | Purpose |
|---|---|
| `ftsystem.o` | FreeType allocator and stream system |
| `ftbase.o` | face, size, glyph, outline, and module core |
| `truetype.o` | TrueType `glyf` driver; native bytecode interpreters disabled |
| `sfnt.o` | SFNT table and Unicode cmap parsing |
| `autofit.o` | automatic hinter fallback |
| `raster.o` | monochrome outline renderer |
| `smooth.o` | normal anti-aliased renderer used by `FT_LOAD_RENDER` |

The OFF control additionally pulls `ftinit.o`, `type1.o`, `cff.o`,
`type1cid.o`, `pfr.o`, `type42.o`, `winfnt.o`, `pcf.o`, `bdf.o`,
`pshinter.o`, `ftgzip.o`, `ftlzw.o`, `psaux.o`, and `psnames.o`.

`psnames.o` is not part of the retained closure. The embedded face has native
Unicode format 4/12 cmaps and a version 3 `post` table with no glyph-name
payload, and the launcher does not call the glyph-name API. The format guard in
`test_freetype_minimal.py` rejects a CFF/non-TrueType replacement before that
assumption can silently change.

Only the normal class from `smooth.o` is registered. GRRLIB always uses
`FT_LOAD_RENDER`, whose default target is normal grayscale; it never requests
LCD or vertical-LCD rendering. The source guard rejects introduction of either
LCD target without a corresponding allowlist review. All three implementations
remain in the same old monolithic archive object, but avoiding the two unused
class instances still saves 128 bytes of module-record heap payload.

## Rendering equivalence

### Module allowlist

`verify_freetype_minimal.c` was built against the exact FreeType 2.4.12 source
with the committed `ftoption.h`. One library instance received the stock full
module list. A second instance used the actual `SusamuneFreeType.c`
initializer and cleanup path.

The oracle rendered every one of the current font's 2,373 mapped Unicode
codepoints at 8, 10, 12, 14, 16, 18, 20, 24, 32, 48, and 64 pixels. It compared
glyph indices, every public glyph metric, linear and fitted advances, bitmap
dimensions, pitch, pixel mode, grayscale count, placement, all bitmap bytes,
and adjacent-pair kerning. It also compared the missing-glyph path at every
size. All **26,103 mapped glyph-size cases**, plus the eleven missing-glyph
cases, matched exactly.

The tested font snapshot was 189,844 bytes, SHA-256
`DF7CBEB02E1A2017E48DEB2E5847BAEB3F0E8DE89880B4835EF0FB7DCF492DA6`.
The deterministic archive was 117,227 bytes, SHA-256
`5E3FFC3A91316DF9608627F711F35E522A6F7417871C448BEAB3E8BF3D130A86`.

### Unpatented-hinter removal

A second harness emitted a deterministic transcript from the control and
no-hinter configurations. It exercised the launcher's actual five registered
module classes and the same 2,373 mapped codepoints, eleven sizes, and missing
glyph path: **26,114 glyph-size cases** in total. Each record contains the
glyph index, all public slot metrics, linear and fitted advances, bitmap
geometry and placement, every bitmap byte, and adjacent-pair kerning.

The 13,030,094-byte rendering payloads were byte-identical, SHA-256
`FAFDD6C142228B7B86E5AE945F33E0053E30C0D88984CBBCDDECD0B5E8F95E10`.
There was no rendering mismatch. The only full-transcript difference was byte
17 in the face metadata: `face_flags` changed from `0x081D` to `0x001D`,
clearing `FT_FACE_FLAG_HINTER` because the driver no longer advertises a
native hinter. The launcher does not inspect that flag, and the embedded face
uses the same auto-hinted rendering path in both configurations.

## Cross-build measurement

Both sides below were rebuilt from the same source tree and shared launcher
blobs. Only `SUSAMUNE_MINIMAL_FREETYPE` differed.

| Measurement | Full registration | Allowlist | Delta |
|---|---:|---:|---:|
| ELF `.text` | 892,896 | 717,664 | -175,232 |
| ELF `.rodata` | 511,048 | 430,840 | -80,208 |
| ELF `.ctors` | 24 | 12 | -12 |
| ELF `.bss` | 529,312 | 529,312 | 0 |
| `boot.dol` | 1,418,976 | 1,163,520 | **-255,456** |
| linked FreeType members | 21 | 7 | -14 |
| module-record heap payload | 968 | 408 | -560 |

The independent ELF-to-DOL verifier accepted both artifacts. The control
contained ten retained sections with 1,418,652 source bytes and eight zero
alignment bytes. The allowlist contained ten retained sections with 1,163,200
source bytes and twenty zero alignment bytes. Artifact hashes were:

- control `boot.dol`:
  `9AC0E831C3AA7E9169DA7799A7363A29B5161A4C6784EB0BD231A2C0B971B2C3`;
- allowlist `boot.dol`:
  `D89632D3CFA95C946FF87058FC9B8AC4384F9D3330717C43188D2F03D90AFD62`.

The module-record figures are the big-endian `module_size` fields read from
the committed PPC class records. They are a lower bound on live heap savings:
eleven fewer `FT_Add_Module` allocations also remove their allocator headers
and any driver-specific initialization allocations.

## Upgrade and hardware gates

`FT_Done_FreeType` reads the first `FT_Memory` field from FreeType 2.4.12's
pinned `FT_LibraryRec_` ABI before destroying the library. This preserves the
stock cleanup sequence without vendoring private headers. The source tests pin
the exact library version and hinting configuration. Any FreeType upgrade must
re-audit that field, rerun the exhaustive oracle, and re-measure both builds.

Before a public release, check the launcher on Wii and vWii at its normal
16-pixel size, including ASCII, accented Latin, Greek, Cyrillic, Arabic,
Armenian, Georgian, Lao, arrows, and missing-glyph fallback. This is the final
hardware gate; the host oracle and identical PPC rendering objects make a
rendering difference unlikely, but they do not replace a console smoke test.
