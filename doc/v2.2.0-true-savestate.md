# Archived V2.2.0 savestate design note

> **Archived scope note:** this draft is not a V2.2 deliverable. Moonshine
> keeps its current same-scenario savestate, which remains the supported design;
> no emulator-style replacement work is planned for Pre-Release 1.

## Status and recommendation

This is retained as a historical design note, not active research or an
implementation claim.

Moonshine's current savestate is a deliberately bounded **gameplay checkpoint**.
It restores the stage heap, selected game globals, and eight root-heap objects at
a safe point in a loaded scenario. It is not, and cannot become, a complete
machine state by adding more `memcpy` ranges to `savestate.cpp`.

There are two materially different paths:

1. **Dolphin:** delegate the request to Dolphin's own `State` subsystem. Dolphin
   already coordinates its CPU, DSP, GPU, and I/O workers and serializes the
   emulated CPU, memory, event queue, devices, and video backend. A tiny,
   optional mailbox bridge can make the in-game bind request that host
   operation.
2. **Wii/Nintendont:** build a cooperative platform checkpoint shared by the PPC
   mod and the ARM kernel. The PPC must park on a restore island, while the ARM
   kernel freezes or serializes its DI/SI/EXI/HID/FatFS work and streams a
   versioned state file. Graphics and DSP state are the hardest remaining
   domains. Until both have a proven capture/restore contract, the result must
   not be described as perfect.

The realistic long-term console target is **deterministic continuation from a
documented frame barrier on any game screen**. Literal arbitrary-instruction
capture and restoration of all physical Flipper/DSP state is a separate,
substantially harder target and may not be practical on retail hardware.

## Terms used here

- **Semantic checkpoint:** enough application data to reproduce the practice
  situation, with selected subsystems reset or reconciled. This is the current
  Moonshine model.
- **Frame-barrier platform state:** the complete future-visible state of the
  guest, captured after concurrent processors and I/O have reached a defined
  boundary.
- **Instruction-boundary state:** CPU execution can resume at the precise saved
  instruction, including an in-progress frame and pending device work.
- **Perfect:** after loading and replaying the same input, all guest-observable
  future behavior is identical. Past photons, audio samples, physical disc
  rotation, a real card already written, and controller radio state cannot be
  rewound. They must be virtualized or explicitly excluded from this promise.

## What the historical V2.1.0 baseline captures

The current contract is defined in [`src/savestate.cpp`](../src/savestate.cpp):

1. `gpApplication` (`sizeof(TApplication)`, currently `0x48`).
2. Selected game-owned `.bss`, `.sdata`, and `.sbss` ranges. JP excludes two
   audio-global ranges. US and PAL currently use one contiguous game-BSS range.
3. The four-byte MSL `rand()` seed when **Save RNG state** is enabled.
4. Eight root-heap targets reached through global pointers:
   `TFlagManager`, `TTimeRec`, `SMSRumbleMgr`, four `TMarioGamePad` objects, and
   the fader. Their combined declared size is `0xFC8` bytes.
5. The entire current `JKRSolidHeap`, from the heap object through `mEnd`.

The snapshot is accepted only when the magic, snapshot version, region, current
heap address, heap size, area, and episode match. Save/load are rejected while
the setup thread or intro is active. Load waits for the game card worker to be
idle, stops game audio, executes a `GXDrawDone` barrier, disables PPC
interrupts, restores the ranges, writes them back from D-cache, invalidates the
texture cache, and invokes feature-specific post-load reconciliation.

This is a sound design for fast same-scenario practice. Its explicit gates and
resets are evidence of the domains that byte-copying alone cannot safely
restore.

### Exact fixed payload cost

With the RNG range enabled and every pointed allocation initialized, the fixed
payload before the stage heap is:

| Region | Header | Game/static + app + RNG | Pointed targets | Fixed total |
| --- | ---: | ---: | ---: | ---: |
| JP | `0x100` | `0xF5F8` | `0xFC8` | `0x106C0` = 67,264 bytes |
| US | `0x100` | `0x2914` | `0xFC8` | `0x39DC` = 14,812 bytes |
| PAL | `0x100` | `0x2924` | `0xFC8` | `0x39EC` = 14,828 bytes |

JP is larger because link ordering places substantially more game BSS before
the first system-owned symbol, even after the two audio carve-outs.

## Dolphin's serialization contract, in order

Dolphin does more than serialize objects. It first establishes a concurrency
contract. `Core::PauseAndLock` pauses and locks the CPU, then DSP/audio, then
FIFO/video. CPU is unlocked last. `State::SaveAs` and `State::LoadAs` route the
operation through `Core::RunOnCPUThread`.

Its byte format is not a console format to copy: it includes emulator-owned
objects, JIT/backend state, and host configuration assumptions. The reusable
parts are its state-domain inventory, ordering constraints, validation, and
transaction model.

`State::DoState` then serializes in this exact top-level order:

| Order | Domain | Important contents or reason |
| ---: | --- | --- |
| 0 | Mode and memory geometry | Wii/GC mode and real MEM1/MEM2 sizes are checked before mutation. |
| 1 | Movie/input recording | Must precede video because video load redraws a window using the restored frame number. |
| 2 | Video backend | Runs first among emulated subsystems so caches can be cleared and modified data written back to RAM. |
| 3 | Core timing | Global virtual time, slice/downcount basis, timebase/decrementer basis, and the named pending-event heap. It precedes hardware because controller restore can schedule events. |
| 4 | Hardware aggregate | Restored before PowerPC because restored CPU cache state can require a flush against restored hardware memory. |
| 5 | PowerPC | Architectural and cache/MMU state. |
| 6 | Wiimote (Wii only) | Remote device state. Not used by a normal GC-mode Sunshine state, but part of the generic contract. |
| 7 | Gecko | Code-handler state. |
| 8 | Achievements, if compiled | Host feature state. |

`HW::DoState` expands order 4 as follows:

1. Main memory (allocated RAM image, locked-cache aperture, optional fake VMEM,
   and EXRAM when present).
2. Memory-interface protection, interrupt, and timing registers.
3. Video interface registers and exact half-line/tick phase.
4. Serial interface channels, device types, device state, transfer buffers,
   polling, and status registers.
5. Processor interface interrupt cause/mask, FIFO pointers, errors, and reset
   state.
6. ARAM, DSP DMA/audio DMA registers, mailboxes, DSP core registers, DSP IRAM,
   and DSP DRAM.
7. DVD interface registers, streaming/DTK state, drive/error state, pending
   reads/results, and ADPCM decoder state. The backing disc itself is validated,
   not serialized.
8. The partial write-gather pipe and byte count.
9. EXI channels and their concrete devices, including card/RTC device state.
10. Audio interface counters, interrupt timing, rates, volume, and mixer state.
11. HSP device state.
12. Wii IPC and IOS/HLE state when running in Wii mode.

`VideoCommon_DoState` expands the video domain into:

- BP, CP, and XF register memories;
- one MiB of emulated texture memory and TMEM tracking metadata;
- FIFO, command-processor FIFO pointers/interrupt state, and pixel-engine
  tokens/interrupts;
- pixel, vertex, and geometry shader-manager state;
- unsubmitted vertex-manager data;
- EFB color/depth contents when **Save Texture Cache to State** is enabled
  (it is enabled by default);
- copied or invalidated texture-cache entries and their references;
- presenter, frame-dumper, bounding-box, widescreen, and XF-derived state.

`PowerPCManager::DoState` includes GPRs, PC/NPC, CR, MSR, FPSCR, pending
exceptions, downcount, XER components, paired-single/FPR state, segment and
special-purpose registers, TLB entries, page-table state, load-reservation
state, I-cache, D-cache, MMU-derived mappings, and JIT state. By comparison, an
SDK `OSContext` is useful but incomplete: it captures ordinary registers,
FPR/paired-single state, SRR0/SRR1, and GQRs, but not the whole MMU/cache/device
contract.

Finally, Dolphin treats state persistence as a transaction:

- capture is dispatched on the CPU thread; concurrent video and I/O work is
  synchronously paused, drained, or joined by the owning subsystem;
- LZ4 compression and file writing happen after capture on a worker;
- output goes to a temporary file and is renamed on commit;
- load validates game ID, state format, mode, and memory geometry;
- an undo state is captured before load; a failed partial load is rolled back.

These are correctness properties, not optional polish.

## Gap analysis: current checkpoint versus a platform state

| Domain | Current Moonshine behavior | Required for a full state |
| --- | --- | --- |
| Remaining MEM1 | Only selected globals, pointed objects, and stage heap are copied. | All mutable RAM, including low memory, root heap, untracked allocations, stacks, SDK/JSystem globals, writable data, and any locked-cache backing. Immutable code may be validated instead of duplicated. |
| Current CPU | The save/load C function continues normally; no architectural context is serialized. | Exact GPR/FPR/PS/CR/XER/LR/CTR/PC/MSR context, timebase/decrementer relation, SPR/SR/BAT/TLB state or strong invariants proving they are constant, reservation state, and canonical cache handling. |
| PPC threads/OS | Interrupts are disabled only around the copy. OS queues and most system globals are intentionally excluded. | Every guest thread context and stack, scheduler queues, alarms, mutexes, condition variables, message queues, pending callbacks, and interrupt state, or a quiescence protocol that safely reconstructs them. |
| Graphics | Load is delayed until `GXDrawDone`; RAM texture bytes are restored and the texture cache is invalidated. | FIFO/gather bytes and pointers, CP/PE interrupts and tokens, BP/CP/XF registers, TMEM, EFB color/depth, and a defined restore/replay sequence. A drain gives a clean boundary but cannot reproduce an arbitrary mid-command instant. |
| Audio/DSP | Game sounds are stopped and the DAC DMA is temporarily muted. JP audio globals are deliberately not restored. | ARAM, DSP registers, mailboxes, DMA phase, DSP IRAM/DRAM, AI counters/interrupt phase, and mixer/output reconciliation. Resetting audio is useful but is not a perfect state. |
| Timing/interrupts | One game stopwatch is reconciled against wall time; device phase is live. | One saved virtual-time origin shared by TB/DEC, VI half-lines, alarms, AI/DSP, SI/EXI/DI completion, CP/PE tokens, and kernel event deadlines. |
| DVD/DI | Stage loads are excluded; no drive state is captured. | Current command, offsets, DMA destination/remaining bytes, streaming/DTK state, result queues, interrupt deadlines, disc identity, and a policy for a real disc whose physical rotation cannot rewind. |
| SI/controllers | Four game pad objects are copied. | SI registers/buffers, poll phase, pending transfer and interrupts, Nintendont controller translation state, HID/BT queues, rumble state, and a policy for changed physical input on resume. |
| EXI/card/RTC | Load waits for the game card manager to report idle. | EXI registers/transfers/interrupts, Nintendont card-emulation cursor and dirty state, RTC/SRAM state, and isolation from irreversible writes to a real card. |
| Nintendont ARM kernel | Not part of the snapshot. It remains live while the PPC copy runs. | A logical serializer for the ARM main loop, DI worker, HID workers, emulated DI/SI/EXI state, pending IOS messages, FatFS ownership, interrupt proxy state, and deadlines. Raw-copying ARM BSS/stacks would restore stale IOS handles and queues and is unsafe. |
| Moonshine runtime in MEM2 | Persistent settings, PBs, ghosts, mailboxes, and the snapshot itself stay live by design. | An explicit per-domain policy: restored, retained, or reconciled. The control/restore island and state storage must remain outside the state being overwritten. |
| External world | Continues normally. | Validate or virtualize ISO/disc identity, storage contents, memory-card view, clock, controller attachment, and output. A state cannot make already-emitted audio/video disappear. |

The Nintendont side is not theoretical background. The fork's
[`launcher/kernel/main.c`](../launcher/kernel/main.c) creates a separate DI
thread, initializes DI/EXI/SI/HID, proxies device interrupts, and services
FatFS-backed Moonshine mailboxes only when no asynchronous DI read owns FatFS.
[`launcher/kernel/kernel.ld`](../launcher/kernel/kernel.ld) assigns the ARM
kernel code, data/BSS, and several stacks to `0x12F00000..0x13000000`. Those
threads and IOS resources must participate in a complete checkpoint.

## Storage arithmetic

### Current reservation

The console snapshot window is:

```text
0x91F00000 .. 0x92EF0000
size 0x00FF0000 = 16,711,680 bytes = 15.9375 MiB
```

Its exclusive end is the 64 KiB configuration/runtime block, followed by the
ARM kernel at `0x92F00000` (`include/susamune/mem2_map.h`). It cannot grow
without displacing live Nintendont or Moonshine owners.

### Straight raw console envelope

A straightforward full-memory representation, before device structures and the
ARM kernel are considered, is:

| Raw domain | Bytes | MiB |
| --- | ---: | ---: |
| Retail MEM1 | `0x01800000` = 25,165,824 | 24.0000 |
| GameCube ARAM | `0x01000000` = 16,777,216 | 16.0000 |
| Canonical EFB color + depth (`640 * 528 * 6`) | 2,027,520 | 1.9336 |
| Texture memory | `0x00100000` = 1,048,576 | 1.0000 |
| DSP IRAM + DRAM | `0x00004000` = 16,384 | 0.0156 |
| **Subtotal** | **45,035,520** | **42.9492** |

The EFB row uses Dolphin's software backend's 24-bit color plus 24-bit depth
canonical representation. A console serializer may choose a different packing,
but it cannot omit the hidden color/depth state and remain equivalent.
The fork's [`launcher/loader/source/main.c`](../launcher/loader/source/main.c)
also makes the ARAM backing explicit by clearing `0x90000000..0x91000000` as
ARAM before launch.

This exceeds the current window by 28,323,840 bytes before CPU context, device
registers, pending queues, format metadata, kernel logical state, compression
workspace, or rollback space.

Compression is useful but not a capacity proof. Arbitrary RAM can be
incompressible and LZ4's worst case is slightly larger than its input. A
console platform state therefore needs chunked streaming to SD/USB, or a much
larger independently verified memory reservation. Streaming is the safer
architecture because it also avoids a second full-RAM undo buffer.

For scale, Dolphin's GC/MMU-off raw memory serializer visits 32 MiB of allocated
RAM, 256 KiB of locked-cache aperture, 32 MiB of fake VMEM, and 16 MiB of ARAM.
Adding the same EFB/TMEM/DSP baseline yields about 83.20 MiB before variable
texture-cache and device data. Dolphin can afford this in host memory; the Wii
cannot copy that architecture literally.

## Feasibility by target

### Dolphin: high feasibility

Dolphin already owns every emulated subsystem and has the necessary thread
locks. The safest integration is not to duplicate Dolphin's serializer inside
the game. It is an optional host bridge:

1. Reserve a cache-line-separated request/ack mailbox at a stable address.
2. The mod writes `{command, slot, sequence}` for save or load.
3. A small Dolphin fork polls it at a CPU-thread-safe boundary and invokes
   `State::Save(system, slot)` or `State::Load(system, slot)`.
4. For save, the host clears/acknowledges the request before serialization so
   the saved memory image cannot retrigger itself after load.
5. Host-only `last_consumed_sequence` state prevents duplicate dispatch. It is
   intentionally outside emulated memory.
6. Dolphin's normal game-ID, state-version, mode, and memory-geometry checks
   remain authoritative.

This produces an actual Dolphin savestate and preserves much more than an
in-game clone ever could. It is tied to compatible Dolphin state versions and
settings, like any normal Dolphin state. Built-in Dolphin hotkeys remain the
zero-code fallback.

### Wii/Nintendont, frame barrier: difficult but technically plausible

Nintendont already controls the device emulation layer and the ARM side of
storage, while Moonshine already has a post-render `GXDrawDone` hook and a
cache-line-safe mailbox design. Those are useful foundations.

A deterministic, frame-boundary platform state is plausible if all of these
are solved:

- a PPC restore island and stack outside restored memory;
- a complete, validated MEM1/ARAM stream;
- a two-processor freeze/ack protocol;
- logical serialization of Nintendont's pending device work;
- one virtual-time basis for all restored deadlines;
- reproducible GPU state, including EFB/TMEM and register shadows;
- reproducible DSP state, or an honestly weaker state class that resets audio;
- transactional storage with corruption and power-loss behavior;
- compatibility fingerprints for game, mod, kernel, and relevant config.

### Wii/Nintendont, literal arbitrary instruction: low feasibility

An in-game bind is sampled by game code, so it cannot request a state from an
arbitrary instruction. An interrupt/exception hook could capture an
`OSContext`, but some regions run with external interrupts masked, DMA and the
GPU/DSP continue independently, and the handler itself needs a stack and
device-consistent boundary.

More importantly, retail software does not expose Dolphin-like read/write
access to every internal GPU and DSP pipeline latch. Draining and replaying
creates a useful boundary, but it changes an arbitrary mid-command state into
a later quiescent state. That can still satisfy an “any game screen” UX; it does
not satisfy a bit-exact arbitrary-instruction claim.

## Proposed staged architecture

### Stage 0 — harden the current semantic checkpoint

Keep the same-scene contract, the current update-time save point, and the
post-render load barrier. Before widening scope:

- add a stored payload length and validate every region count, destination,
  size, offset, and addition for overflow before the first write;
- accept destinations only from a fixed per-build allowlist, not arbitrary
  addresses stored in the header;
- add header/directory integrity and optional payload/chunk CRCs;
- add a build fingerprint beyond the regional numeric ID;
- record why a save/load was rejected and the active game/ARM phase in debug
  builds;
- retain commit-magic-last behavior.

This improves failure safety without pretending to expand coverage.

### Stage 1 — inventory and deterministic replay harness

Create a debug-only state census before changing the format:

- enumerate game and system heaps and classify every root allocation;
- enumerate active PPC threads, their contexts, and stack ranges;
- log active alarms, message queues, and pending DVD/CARD work at the barrier;
- hash canonical state once per frame during a record/replay test;
- maintain a domain ledger with one of `restored`, `retained`, `reset`,
  `reconstructed`, or `external` for every mutable owner.

Unknown ownership is a release blocker for a stronger state class.

### Stage 2 — establish the restore island

Load a tiny, immutable PPC assembly stub and stack into a reserved MEM2 control
island that is never part of a state payload. Enter it through an absolute
`mtctr`/`bctr` transfer. It must:

1. save an SDK `OSContext` plus explicitly selected SPR/timebase/cache state;
2. disable interrupts and scheduler dispatch;
3. canonicalize dirty D-cache lines;
4. issue the ARM doorbell and park without touching restored RAM;
5. on load, invalidate appropriate caches and transfer with `OSLoadContext`
   only after all RAM/device domains are coherent.

Saving can read the code that is currently executing, but loading cannot safely
overwrite its own code or stack. The control island solves that self-overwrite
problem. If MEM2 execution proves unreliable in the Nintendont memory mode, use
an immutable MEM1 island excluded from the payload and validate its exact hash
before load; do not rely on “the next few instructions are probably cached.”

### Stage 3 — add a two-processor state coordinator

Use a cache-line-owned mailbox, following the existing configuration mailbox's
PPC/ARM ownership rule. Suggested phases:

```text
IDLE
  -> PPC_PARK_REQUESTED
  -> ARM_QUIESCED
  -> DEVICES_CAPTURED
  -> MEMORY_STREAMING
  -> COMMITTED
  -> IDLE

LOAD_VALIDATED
  -> ARM_QUIESCED
  -> PPC_PARKED
  -> DEVICES_PREPARED
  -> MEMORY_RESTORED
  -> CONTEXT_RELEASED
  -> IDLE
```

The ARM coordinator must stop accepting new DI/HID/FatFS work and either drain
or serialize each pending operation. Blindly copying ARM BSS, stacks, or IOS
message-queue handles is forbidden. `launcher/kernel/main.c` and the DI/HID
worker code need explicit logical `measure/write/read/verify` routines, similar
in spirit to Dolphin's `DoState` functions.

Mirror Dolphin's lock order where possible: stop PPC production first, then
DSP/audio, then GPU/FIFO; restore virtual timing before devices; release PPC
last.

### Stage 4 — stream a transactional state file

Use a directory of typed chunks, not destination addresses supplied by the
file. A minimum header should identify:

- format version and header size;
- game ID, disc revision, region, and executable fingerprint;
- Moonshine build fingerprint and Nintendont state ABI/kernel fingerprint;
- state class (`semantic`, `frame-platform`, or future `instruction-platform`);
- relevant launch configuration and device types;
- saved virtual-time origin;
- raw and stored payload sizes;
- chunk count, directory CRC, and whole-state or per-chunk CRCs.

Each chunk needs a domain ID, codec, raw length, stored length, flags, and CRC.
The domain ID selects compiled restore code; a corrupted file must never be
able to choose a write address.

MEM1/ARAM chunks can use a fixed-size page map with four explicit page kinds:
literal, zero-fill, verified immutable baseline, and excluded control-plane.
Baseline pages save substantial space only when the executable/disc/mod hashes
prove exactly which bytes will reconstruct them. A page must never be omitted
merely because it happened to look unused during one capture.

Save to the inactive member of an A/B generation pair, flush it, then
write/validate its final directory and commit marker. On load, choose the
highest completely valid generation. This keeps the previous state without
assuming a FAT rename is power-loss atomic. Load should validate the complete
header and directory before parking the machine. For a no-undo streaming
restore, validate every chunk CRC in a first pass, rewind, then mutate in a
second pass. A read failure after mutation must fail closed into a controlled
reboot, not resume a half-restored machine.

### Stage 5 — graphics and DSP proof

Graphics work should start only at the post-`GXDrawDone` barrier:

- prove FIFO/gather emptiness and capture pointer/token/interrupt state;
- identify a complete software shadow for BP/CP/XF state or record a bounded
  replay stream;
- prototype whole-EFB capture/restore with the retail SDK's `GXPeekARGB`,
  `GXPeekZ`, `GXPokeARGB`, and `GXPokeZ` path. It exposes both hidden planes but
  performs per-pixel MMIO, so fidelity and latency must be measured. Compare it
  with bulk `GXCopyTex`, whose format conversion and one-plane-at-a-time
  behavior need separate proof;
- capture/recreate TMEM and invalidate caches in a defined order;
- test render-to-texture users, pollution/goop, bounding/depth behavior, and
  pending GX tokens.

DSP work needs an equally explicit answer:

- halt at a documented boundary;
- capture ARAM, DSP IRAM/DRAM, mailboxes, DMA registers and phase, AI sample
  counters, and pending interrupts;
- test the SDK's declared DSP halt/reset/task-resume interface and the task
  descriptors' IRAM/DRAM backing addresses, without assuming those expose the
  live DSP PC, register file, stacks, or pipeline latches;
- prove whether the retail DSP exposes enough state to resume the microcode;
- if it does not, define a weaker **audio-reset platform state** and keep the
  word “perfect” out of its UI and release notes.

### Stage 6 — widen supported game contexts

Only after the platform state passes determinism tests should the current
`gpMarDirector`/same-scenario gate be widened. Add contexts in increasing risk:

1. loaded gameplay, pause, and dialogs;
2. shine/cutscene/fader states;
3. stage exit and fully loaded stage entry barriers;
4. title, file select, options, and movies;
5. async setup/loading, only if the setup/DVD threads are genuinely serialized.

“Anywhere” should mean every context in a published matrix, not an untested
absence of guards.

## Concrete V2.2 preliminary work

The following is suitable groundwork for V2.2 without claiming a true console
state:

1. Land this domain/ordering/storage study as the architectural boundary.
2. Add a debug-only snapshot census and payload-size report; do not widen the
   supported save window yet.
3. Harden the existing header's bounds/integrity checks while preserving its
   same-scenario semantics.
4. Specify a state ABI and cache-line-owned PPC/ARM coordinator mailbox in a
   header shared by the mod and kernel, but keep it inactive until both sides
   implement timeout-safe quiescence.
5. Prototype the restore-island context save/load in an isolated diagnostics
   build that never writes a production state.
6. Prototype the Dolphin mailbox bridge in a pinned Dolphin fork. This is the
   shortest path to an in-game bind that creates a genuine emulator state.
7. Add the deterministic replay and fault-injection test harness before adding
   more state domains.

Items 2–7 are future implementation tasks; this pre-release research does not
silently enable any of them.

## Required invariants

A platform-state implementation must enforce all of these before mutating live
state:

- exact game ID, disc revision, region, executable fingerprint, mod build, and
  kernel state ABI match;
- exact relevant Nintendont configuration and device-type compatibility;
- complete file commit marker, directory validity, lengths, arithmetic, and
  checksums;
- restore island and stack are outside every restored destination;
- no destination overlaps the state control plane or ARM kernel unless handled
  by that domain's logical serializer;
- PPC, DSP, GPU, DI, SI, EXI, HID, and storage services have acknowledged the
  same state epoch;
- cache ownership and cached/uncached alias rules are respected on every
  PPC/ARM handoff;
- all device deadlines are expressed relative to one restored virtual-time
  origin, not elapsed wall time;
- external ISO/disc/card identity is validated before load;
- a timeout aborts before mutation, or after mutation enters controlled reboot;
- feature-owned mod state has an explicit restore/retain/reconcile policy.

## Test plan

### Determinism oracle

At a supported barrier, save, run a fixed input movie for `N` frames, load,
replay it, and compare per-frame hashes for:

- canonical mutable MEM1 and ARAM;
- CPU context and selected SPR/MMU/cache metadata;
- virtual time and pending-event directory;
- logical DI/SI/EXI/AI/DSP/VI/CP/PE state;
- EFB color/depth and output-frame hashes;
- audio sample hashes after the documented resume boundary.

A screenshot match is not sufficient; divergent hidden timers or queues can
fail minutes later.

### Context matrix

Exercise JP, US, and PAL in each implemented context: normal gameplay, pause,
dialog, Yoshi/nozzle interactions, boss states, water/pollution effects,
cutscenes, shine spawn/get, faders, blue card screen, stage exit/entry, title,
file select, options, and movie playback. Loading/intro contexts remain expected
rejections until their state domains are implemented.

### Pending-work matrix

Force a state near every interrupt or async edge:

- VI field/half-line change;
- SI poll and controller attach/detach;
- EXI transfer/card status/RTC read;
- DI DMA and streaming audio completion;
- AI/DSP DMA block and mailbox exchange;
- GX token, finish interrupt, EFB copy, and partially filled gather pipe;
- setup, card, THP, draw-sync, and audio worker thread wake/sleep boundaries;
- ARM DI, HID, ghost/PB/config save, and FatFS ownership boundaries.

### Storage and compatibility faults

- truncate every chunk boundary and corrupt every header/directory field;
- inject read, write, flush, full-device, and removal failures;
- verify the previous committed slot survives every failed save;
- verify no rejected load mutates live state;
- test the wrong region, revision, ISO, mod, kernel ABI, controller mode, card
  mode, video mode, and state class;
- power-cycle at every boundary between inactive-generation creation and
  commit.

### Longevity

Run at least 1,000 save/load cycles per region, including repeated replay of the
same input. Check heap invariants, ARM/PPC cache coherency, device queue growth,
storage-handle leaks, audio artifacts, and state-file size stability.

## Open research questions and stop conditions

These questions must be answered experimentally before a console full-state
milestone is named:

1. Can a PPC stub execute reliably from the selected MEM2 control island under
   every supported Nintendont/Wii/Wii U mode?
2. Which Gekko SPR/BAT/cache fields vary during Sunshine, and which can safely
   be validated rather than restored?
3. Can Flipper EFB color **and depth**, BP/CP/XF state, and TMEM be captured and
   restored without losing guest-visible behavior?
4. Can the physical DSP microcode context be halted, read, and resumed, or must
   console states always document an audio reset?
5. Which Nintendont DI/SI/EXI/HID pending operations can be serialized, and
   which must reach an idle boundary?
6. How should real-card writes be isolated so a load never makes RAM disagree
   with an irreversible external save?
7. What is the measured raw/compressed size and save/load latency across the
   largest JP/US/PAL stages and high-entropy EFB/ARAM workloads?

If questions 3 or 4 have no complete hardware mechanism, stop at an honestly
named frame-boundary or audio-reset checkpoint. Do not turn a successful
thousand-frame smoke test into a “perfect” guarantee.

## Protected timing scope

This study does not modify or propose an implicit rewrite of Moonshine's timer,
QFT, SplitStats, or SplitEvents code. Any implementation with timer-visible
semantics remains separately gated and requires explicit approval.
