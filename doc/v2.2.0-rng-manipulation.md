# V2.2.0 RNG manipulation reconnaissance

This is the implementation plan for deterministic and selectable randomness in
Sunshine. It deliberately does not change the timer, and it does not propose
that savestates copy OS, CARD, renderer, or audio-thread state.

## Evidence and confidence

The results below use three independent sources:

- `doldecomp/sms` at commit
  `826aeec7f78b7e167fe710a3141113dea3a5badf` for algorithms, type layouts, and
  the parts of the game which are decompiled.
- `maps/jp.map`, `maps/us.map`, and `maps/pal.map` for retail symbols and
  regional addresses.
- Clean retail DOLs extracted from the three user-owned discs. Their SHA-1s
  were JP `9f5a8caf56f5356aeac9d3ed28bf8de976a03625`, US
  `a6782903ef79d4196c8489ecb1b57decb5b3728f`, and PAL
  `a2edfa86880845f663f6f3b49e27cc9409d202bf`. The JP and PAL hashes match the
  decomp project's pinned builds. The decomp has no current US build config,
  so the US map plus clean retail DOL are the evidence for that revision.

`MoveBG/MapObjRicco.cpp`, `MoveBG/MapObjWave.cpp`, and `Animal/Bird.cpp` are
currently empty placeholders in the decomp. Findings for those files are from
the retail instructions and maps, not guessed C. Decompiled helpers marked
`fabricated` or `TODO` were treated as explanatory only; the DOL call audit is
the ground truth for whether retail code actually calls `rand`.

## Executive result

Sunshine does not have one universal RNG:

1. Enemies, bosses, Ricco's fruit launcher and cranes, birds, FLUDD water, NPC
   variation, and many map objects share MSL libc's one 32-bit `rand` state.
2. JPA particles use independent JMath LCGs: one global emitter-seed generator,
   one RNG in every emitter, and a separate global field RNG.
3. Bowser's bathtub water has three heap-resident JMath RNGs of its own: one in
   the manager and one in each of its two child water objects.
4. Audio has several independent JMath RNGs. They must stay outside gameplay
   manipulation and outside savestate restoration while audio itself is reset
   rather than snapshotted.
5. CARD has a second global named `next` which happens to use the same libc LCG
   constants. It is not gameplay state and must never be mistaken for the MSL
   seed.

The implementation plan is now a hybrid, chosen per semantic boundary:

1. King Boo and Petey use narrow boss-specific hooks. Their requested outcomes
   are a reel result, a nerve branch, and graph successors, not generic random
   numbers.
2. Ricco fruit, birds, and model water use confirmed direct `bl rand` sites for
   tiny actor-aware thunks. Each thunk calls retail `rand` exactly once, then
   optionally substitutes the 15-bit return. Ricco cranes capture their stable
   roll at two such sites and enforce the chosen band through two validated
   class-control slots. This preserves the shared seed and gives each policy
   the real actor/name without a heap scan or global current-actor variable.
3. A full `rand`-entry detour remains useful for an instrumentation build and
   seed lab, but is not the release baseline. The audit found 315 direct sites
   in JP/US and 308 in PAL; making every one pay release-time classification is
   unnecessary when only a small confirmed set is controllable.

This design keeps every unselected role byte-for-byte retail at the call
boundary, and keeps the global stream aligned even while a chosen result is
forced. Control-flow changes can still alter how many later calls execute; that
is intrinsic to the selected behavior and must be visible in validation.

### The gameplay libc generator

`TApplication::initialize` seeds libc once with `srand(OSGetTick())`
(`System/Application.cpp:250`). `MarioUtil/RandomUtil.hpp`'s `MsRandF`,
`MsRandI`, and `TMsRange::rand` all ultimately call the same libc function.
The retail branch audit finds exactly one direct `srand` caller in every
revision, this initialization site; stage loads do not deliberately reseed the
libc stream.
No enemy- or bird-local `TRandomFast` object was found in the source tree.
Their object fields store decisions already made, not another PRNG state.

The multiplier is odd, so it is invertible modulo 2^32:

```text
A       = 0x41c64e6d
C       = 0x00003039
A^-1    = 0xeeb9eb65     (mod 2^32)
forward = A * state + C
back    = A^-1 * (state - C)
```

This gives a true one-call Previous operation without a history buffer. Large
positive or negative skips should use affine exponentiation by squaring rather
than looping once per call.

To make the very next `rand()` return a chosen 15-bit value `y`, choose a
canonical post-step state `after = y << 16`, then write:

```text
before = A^-1 * (after - C) mod 2^32
```

There are actually 131072 post-step states for every visible result because
bit 31 and the low 16 bits are discarded. The canonical form is adequate for
a Set Next Output tool. A caller-role return override is preferable for normal
practice because it does not perturb subsequent seed state.

`scripts/rng_lab.py` is the tested host oracle for both the MSL and JMath-fast
generators. It implements exact forward, inverse, and signed O(log N) jumps,
and can construct a pre-state for a chosen visible MSL result. For example:

```powershell
python scripts/rng_lab.py advance msl 0x00000001 1
python scripts/rng_lab.py advance msl 0x41c67ea6 -1
python scripts/rng_lab.py visible 12345
```

The companion tests cover retail vectors, 10,000 randomized inverse checks per
generator, positive and negative iterative equivalence, huge-jump composition,
and every chosen-output boundary. This is an offline planning tool; it does not
patch the game or touch timer state.

## Retail call audit

`scripts/audit_rng_calls.py` scans every DOL text section for direct PPC
branch-and-link instructions to a map symbol, then attributes each call to the
smallest containing map symbol. The reproducible command is:

```powershell
python scripts/audit_rng_calls.py main.dol maps/jp.map --target-symbol rand --group
```

The JP static call-site distribution is:

| Library | Direct sites |
|---|---:|
| Enemy | 186 |
| MoveBG | 57 |
| Animal | 27 |
| Player | 16 |
| NPC | 13 |
| Map | 8 |
| MarioUtil | 6 |
| GC2D | 2 |

JP and US have the same 315 sites and the same per-function counts. PAL lacks
seven JP/US direct calls, all in `hinokuri2.cpp`: `TNerveHino2Stamp`,
`TNerveHino2Damage`, `TNerveHino2PrePol`, `TNerveHino2Pollute`,
`TNerveHino2GraphWander`, `THinokuri2::moveObject`, and

`--include-tail-branches` found no direct non-link `b rand` in any revision, so
all 315/315/308 known direct branches preserve the immediate caller in LR.

## Target reconnaissance

### Ricco fruit launcher

`TFruitLauncher::fireObj` has five static `rand` call sites, at the same
function-relative offsets in all revisions:

| Offset | Role |
|---:|---|
| `+0x134` | First fruit selection |
| `+0x250` | Second selection, only if allocation returned null |
| `+0x36c` | Third selection, only if allocation returned null again |
| `+0x4a0` | Launch Z velocity |
| `+0x4e0` | Launch X velocity |

The selector scales `rand()` to `[0, 100)` with retail single-precision
rounding and compares it with 20, 40, 60, and 80. Exhaustively evaluating all
32,768 legal returns gives the exact buckets:

| Fruit | Type | Inclusive return range | Safe representative |
|---|---:|---:|---:|
| Coconut | `0x40000390` | `0x0000..0x1999` | `0x0800` |
| Papaya | `0x40000391` | `0x199a..0x3333` | `0x2000` |
| Pineapple | `0x40000392` | `0x3334..0x4ccc` | `0x4000` |
| Durian | `0x40000393` | `0x4ccd..0x6666` | `0x6000` |
| Banana | `0x40000394` | `0x6667..0x7fff` | `0x7800` |

The actor mapping is independently confirmed by `MoveBG/MapObjInit.cpp` and
the mod's `include/SMS/MoveBG/ResetFruit.hxx`.

Normal success consumes three outputs: one selection and two velocity values.
Success on attempt two or three consumes four or five. Total allocation failure
consumes exactly three selectors and no velocity calls. A forced-fruit policy
must therefore cover all three selection sites for one `fireObj` event. If a
particular fruit pool is exhausted, forcing it should fail cleanly after the
third lookup; the RNG layer must not fabricate or reuse an actor.

The queued override needs a tiny event state machine, not a generic consume-once
flag. Keep the chosen bucket armed across selection attempts 1-3. Clear it when
the first velocity site (`+0x4a0`) proves an allocation succeeded, or
immediately after returning the third forced selection (the function has no
fourth attempt). This also prevents an all-failed request leaking into the next
button press.

The implemented `Durians only` policy is a role-return override. At all three
selector calls the launcher object is proven live in `r31`, so a shared `r31`
thunk passes both actor and LR role to the resolver. The resolver advances the
retail LCG exactly once and substitutes safe Durian representative `0x6000`.
The same launcher remains armed across allocation retries. Selector three
clears an all-failed event; the first velocity role clears a successful event
and returns its retail value unchanged. The second velocity call is not
hooked. This preserves retail call count and launch physics.

| Function | JP | US | PAL |
|---|---:|---:|---:|
| `TFruitLauncher::fireObj` | `0x801a4fc4` | `0x801cd40c` | `0x801c52c4` |

The hook compares `LR - 4` with `function + offset`; LR itself is the listed
call site plus four.

`TRandomFruit::initMapObj` is a different one-call-at-load map object. It must
not be labelled as the Ricco launcher.

### Ricco cranes

All nine Ricco episodes contain the same five records, byte-identical across
regions and in stable scene order: `crane90 0`, `crane90 1`, `crane90 2`,
`craneUpDown 0`, and `craneUpDown 1`. The names are already populated at the
RNG calls, so a name check is safer than a setup ordinal.

| Function / role | JP call | US call | PAL call | Live object |
|---|---:|---:|---:|---|
| `TCraneUpDown::initMapObj+0xd0` | `0x801a5ed0` | `0x801ce318` | `0x801c61d0` | `r31` |
| `TCraneRotY::load+0x38` | `0x801a625c` | `0x801ce6a4` | `0x801c655c` | `r30` |

UpDown writes current X rotation at `+0x30` as
`lower + (upper-lower)*(y/32768)`. `craneUpDown 0` spans `[-25,45]` and
`craneUpDown 1` spans `[-25,30]`; bounds live at `+0x144/+0x140`. RotY keeps
the authored/base Y angle at `+0x138`, reads a `90` degree upper delta into
`+0x140`, and writes per-instance speed at `+0x144` as
`0.05 + 0.1*(y/32768)`. It does not randomize initial phase. Both controllers
are deterministic after initialization and use state `+0xfc` plus wait timer
`+0x104`; `TCraneCargo` has no direct RNG call.

Initialization control should patch only these two calls, pass the proven
object register through an `r31`/`r30` thunk, call retail `rand` once, then
match the exact object name before substituting the return. No ordinal, heap
scan, or global actor-context variable is needed.

For a live crane editor, resolve the same names through
`JDrama::TNameRefGen::search` after setup and cache pointers only for the
current stage. A phase preset must write angle together with coherent
state/countdown; writing angle alone can cross an old endpoint immediately.
RotY speed is per-instance, while UpDown speed/wait are shared globals.

The retail shared tunables are `mWaitTime__10TCraneRotY`,
`mRotSpeed__12TCraneUpDown`, and `mWaitTime__12TCraneUpDown` at respectively
JP `0x804090c0/c4/c8`, US `0x8040c830/34/38`, and PAL
`0x80403f90/94/98`. They are global behavior tuning, not RNG state.

PR1 implements one stable random speed for each of the five named cranes. The
existing initialization result is retained per actor and mapped across the 20
integer percentages in the selected band: Slowest `1-20`, Slow
`21-40`, Medium `41-60`, Fast `61-80`, or Fastest `81-100`. No additional
`rand()` call is made. RotY control writes the selected fraction of its native
`0.15` maximum to the instance field. UpDown control temporarily scales the
retail shared rotation speed only for the duration of that actor's control
call, then restores the global immediately so the other crane can use its own
roll. Off restores the captured RotY retail speed and leaves the UpDown global
untouched. Changing bands live remaps the retained roll; reloading the stage
creates a new roll through retail initialization.

#### King Boo: fruit every other roll

The stopped-slot result enum is statically closed: result `2` enters the normal
fruit/pepper body in `TBossTelesa::generateSlotItem`; result `0` is coins and
`1/3/-1` use the enemy path. Result `3` is the controlled no-fruit result: it
always takes the enemy path, unlike the coin result whose availability is
filtered by boss state. The narrow intervention is the one
`TTelesaSlot::forceStopSlot(slot, 1)` call in
`TNerveBossTelesaSlotStart::execute`:

| Region | Wrapper call site | Original word | Retail target |
|---|---:|---:|---:|
| JP | `0x802d0f78` | `0x48005e69` | `0x802d6de0` |
| US | `0x800be8e8` | `0x48005e85` | `0x800c476c` |
| PAL | `0x800b7f88` | `0x48005e85` | `0x800bde0c` |

The wrapper calls retail first, then stores either `2` or `3` to
`TTelesaSlot+0x1a4` and arms that reel's targeted-stop state at
`+0x198+reel` and `+0x1a8+reel`. Both state bytes matter: the ordinary retail
stop path clears `+0x198+reel` and leaves `+0x1a8+reel` clear, in which case
`moveObject` never consults the forecast while stopping. Re-arming both
reproduces retail's targeted-stop mode, so the visible drum keeps moving until
its decoded angle matches the controlled result. This preserves every
conditional RNG advance, probability/anti-repeat setup, reel animation, and
the later actual-angle result check. Overriding item generation alone could
show a different roll from the object set it creates; forcing individual RNG
calls would couple the feature to unrelated slot internals.

The phase is stored in bytes proven to be alignment padding in every regional
`TTelesaSlot` constructor: a three-byte marker at `+0x19d..+0x19f` and one
state byte at `+0x1ab`. `TBossTelesa::generateSlotItem` writes the agreed
three-reel result to its owner at `+0x1a8`; the next stop command advances the
phase only when that value equals the previous controlled target. Consequently
an interrupted or skipped no-fruit cycle remains due. The hook site is one
fixed `forceStopSlot(slot, 1)` call, not a per-reel loop, so the acknowledgement
can be consumed only once per new roll.

### Water is three different systems

#### FLUDD/model water

| `+0x1a0` | power tremble |
| `+0x234` | size tremble |

| Offset | Effect |
|---:|---|

| `+0x58c` | tiny ripple on water surface; visual |

Retail/Always/Never`, and `Wall Water: Retail/Always/Never`. Patch the confirmed

`makeEmit` path serves non-FLUDD producers too, so the UI must say **Model
Water**, not promise FLUDD-only, unless a future semantic producer wrapper is
added. Two move roles change the lifetime and travel of collision-capable
water and must not be described as cosmetic.

#### Bowser bathtub water

`TBathWaterManager` is a separate JMath system. It contains `TRandomFast` at
manager `+0x10`. Each of its two heap child `TBathWater` objects has another at
child `+0x68`. All are constructed with seed zero. The manager RNG chooses
periodic jump-drop placement/velocity; child RNGs choose reset/add-drop phase.

The manager and its child arrays are created during stage setup, so they are
inside the stage-heap image and already rewind with a same-scene savestate even
when `Save RNG state` is Off; that setting gates only libc. There is no mapped
singleton pointer. A future live editor should resolve the object named
`バスタブの水` through `TNameRefGen`, clear the cache on setup, and validate the
manager, child array, both children, current stage heap, and regional vtables
before use. First release should expose seed/set/next/previous/signed-jump for
manager, child 0, and child 1; a one-shot jump-drop output needs a narrow inline
periodic-block thunk because these JMath advances are inlined.

#### JPA water effects and map waves

JPA visual water/splash effects use per-emitter JMath RNG, not libc. Every
`JPABaseEmitter` stores its RNG at `+0x21c`; its constructor seeds that word
from `JPAEmitterInfoObj + 0x8`. `JPAField.cpp` has another global fast RNG named
`FieldRand` for random/drag field behavior.

`TMapObjWave` is different again. Its constructor has four libc calls at
`+0xbc/+0xf0/+0x120/+0x148`, writing sine phases `+0x64/+0x68` and texture
phases `+0x6c/+0x70`; `perform`, `updateTime`, and height queries have no direct
RNG calls. Thus the surface's initial conditions are random while subsequent
wave animation/height physics are deterministic from stored state. A live
phase editor should resolve the existing singleton and write those four fields
after construction, preserving all four retail seed advances.

| State/function | JP | US | PAL |
|---|---:|---:|---:|
| JPA emitter seed word | `0x803e6c48` | `0x803fe140` | `0x803f58e0` |
| JPA `FieldRand` | `0x80409d10` | `0x8040e6e0` | `0x80405db8` |
| `TMapObjWave` constructor | `0x801b44f8` | `0x801dca00` | `0x801d48d8` |

The stage heap captures active emitters and their `+0x21c` states because the
JPA pools are allocated from the current stage heap during resource setup.
The two JPA global seed words are outside every current game-only static
range. Capturing exactly those two four-byte words is a plausible savestate
completeness improvement. Do not snapshot the full 0x180-byte
`JPAEmitterInfoObj`: it also contains transient current-emitter/current-field
pointers and rendering context.

## Audio RNG: explicitly out of scope

These independent states are useful for proving that libc is not universal:

| State | JP | US | PAL |
|---|---:|---:|---:|
| `JAIConst::random` | `0x80409a70` | `0x8040e440` | `0x80405b18` |
| JAL `oRandom` | `0x804099b4` | `0x8040e41c` | `0x80405af4` |
| JAS instrument `oRandom` | `0x80409b64` | `0x8040e534` | `0x80405c0c` |
| JAS player `TRandom_enough` | `0x803e6ab8` | `0x803fdfb0` | `0x803f5750` |

The current savestate intentionally calls `stopAllSound()` and excludes live
JAudio state. Restoring these RNGs without restoring DSP/track state would not
make audio deterministic; it would make the reset audio engine inconsistent
with old random state. RNG manipulation must leave them alone.

## Implementation architecture

### Implemented: requested semantic controls

The dedicated `RNG Control` menu now contains:

- King Boo / `Fruit every other roll`;
- Petey / `Disable tornado`;
- Petey / `Route: Off / N1-S1-S2-S3`;
- Ricco Crane / `Random speed: Off / Slowest / Slow / Medium / Fast / Fastest`;
- Ricco Fruit Machine / `Fruit: Off / Durians only`.

The King Boo wrapper always calls retail and, when enabled, alternates fruit
and a guaranteed enemy result while re-arming retail's targeted-stop state.
The no-tornado word is a toggle-driven code patch that restores `0x408000f0`
when disabled. Petey routing extends the existing Pattern Selector graph
wrapper and calls retail graph choice before substituting an adjacent node.
Region-selected sites are covered by source/build oracles; the live
no-tornado writer also refuses to capture or replace an unexpected word.

All five controls are implemented for JP, US, and PAL. They require no heap
allocation, route counter, global RNG detour, or timer/split timing-source
change. Boss controls intentionally call the existing attempt-eligibility
invalidation path described below. The crane
controller uses five fixed BSS records populated only by the retail setup
calls and patches the two exact class-control vtable slots after validating
their retail values. The fruit launcher uses one pending actor pointer only
while `fireObj` retries synchronously; stage setup clears it defensively.

### IL integrity and visible assisted state

King Boo's control and both Petey controls revoke the active attempt's PB,
Records, split, streak, and playlist eligibility every frame they are enabled.
They also lock Creation, force the cached native HUD panes and FLUDD-water
colours to `(255, 0, 0)`, route Moonshine overlay foregrounds through the same
red warning colour, and draw `INVALID IL` after every other overlay. The menu
itself stays readable while open. Colours are snapshotted before the warning
and restored when all boss controls are Off; a fresh-stage baseline plus a
post-savestate-load reapply handles an assisted snapshot loaded after a
same-scenario restart.

Ricco crane speed and fruit selection remain practice setup controls and do
not enable the persistent boss warning. The bind-driven Spawn Yoshi Anywhere
and Regrab Last Held Object actions invalidate only when their prerequisites
pass and the action is actually applied; they do not leave a persistent visual
mode enabled.

### Future phase: actor-aware direct role thunks

Patch only confirmed direct call sites. Three tiny thunks cover the proven live
actor registers:

```text
thunk_r31: mr r3,r31; mflr r4; b resolveRngRole
thunk_r30: mr r3,r30; mflr r4; b resolveRngRole
thunk_r28: mr r3,r28; mflr r4; b resolveRngRole
```

The tail branch preserves the original LR. `resolveRngRole(actor, LR)` calls
the untouched retail `rand` exactly once, validates the regional role plus
actor name/type, and returns either retail or a substitute. Future controls can
use this for:

- the nine direct bird roles plus selected shared `TAnimalBase` roles, using
  actor type `0x00800001` as a second guard;
- five model-water emit roles and the two gameplay survival roles. These are
  global model-water controls unless a producer context is added.

This avoids ordinals, heap scans, register guesses inside generic `rand`, and a
global current-actor stack. A control-flow override may still change the number
of future calls; that intrinsic divergence is logged in validation.

Do not edit policy state while the async setup thread is consuming it. Freeze
next-load choices before transition or queue writes until
`gpMarDirector->_260 != 0`.

### Future phase: exact seed lab and optional trace build

The tested `scripts/rng_lab.py` already provides set/next/previous/signed jump
and chosen-next-output math without touching the game. A runtime lab can expose
the same operations by reading/writing the regional MSL word, but must not race
stage setup.

A full `rand`-entry hook belongs in an instrumentation build only. It must
capture the caller before any helper overwrites LR, perform the exact LCG update
and store, and return retail unless tracing explicitly asks otherwise. Keep a
fixed trace ring in reserved coherent MEM2 and compile it out of release; never
allocate or perform file I/O inside `rand`.

### Future phase: optional decoupled practice streams

For repeatable patterns independent of unrelated activity, maintain small
domain seeds for `Boss`, `Enemy`, `Bird`, `Fruit`, `WaterEmit`, and
`WaterCollision`. A classified call advances both the retail global generator
(discarding its output) and the selected domain generator (returning its
output). Advancing the retail stream preserves call-count alignment for
unclassified systems.

This mode is intentionally non-retail and should be labelled as such. Default
and `Off` must use the exact shared retail stream. A domain mode should never
silently become the default for timing/regression work.

### Runtime/savestate ownership

Persisted settings select UI defaults and are not rewound by a savestate.
King Boo's phase and completion acknowledgement live in the slot and boss
objects on the stage heap, so same-scene savestate loads rewind the sequence
with the fight. A stage-setup reset clears the live pointer guard, making every
fresh fight start with fruit. A successful load explicitly re-adopts a valid
saved marker before the next pull, including after restarting the same
scenario. Because settings themselves are not rewound, loading a snapshot that
contains an older valid marker while the control is currently On resumes that
saved phase even if the control happened to be Off when the snapshot was made;
this preserves the anti-skip sequence. Petey's graph route needs no separate
phase.
Crane records retain a stage actor pointer, its retail speed, and the
initialization roll; these values do not advance after stage setup, and
same-scene savestate loads keep the actor address stable. Stage setup clears all
five records before new actors are created. Ricco fruit-machine state exists
only inside one synchronous `fireObj` call, so it cannot straddle a savestate
action. Future one-shot requests and optional practice domains would need to
rewind:

- queued one-shot values;
- domain seeds and per-domain call counts;
- an armed event's remaining outputs.

Put those fields in one small, versioned runtime block and add that block as a
mod-owned savestate region when the feature lands. Do not snapshot the whole
settings object. Bump the snapshot version if the block layout changes.

For visual completeness, separately capture only JPA emitter seed and
`FieldRand`. Active emitter RNG words and all gameplay actor/water state should
already be in the stage heap. Audio RNG remains excluded.

### Trace mode without permanent MEM1 cost

An instrumentation build should record `{sequence, caller, before, after,
result, area/episode, role}` in a fixed ring. Keep only indices/configuration in
MEM1; put the ring in a reserved/coherent MEM2 diagnostics area or compile it
out of release builds. It must not allocate from the nearly full game heap and
must not perform file I/O from inside `rand`.

The requested King Boo and Petey decisions are statically closed and do not
need an 18-site King Boo trace. Trace mode remains valuable for adding other
enemy outcomes or proving an individual-bird registry under real stage order.

## Validation gates

1. With every RNG option off, compare a debug seed/output trace against retail
   for at least 100,000 calls in JP, US, and PAL. Every post-state and return
   must match.
2. Assert `previous(next(s)) == s` across fixed edge cases and randomized
   32-bit states.
3. Perform consecutive King Boo pulls and confirm fruit, enemy/no-fruit, fruit,
   enemy/no-fruit. Interrupt a no-fruit cycle and confirm no fruit becomes due
   until that cycle completes, with the unforced seed trace still aligned.
4. Complete Bianco 5 Petey: reach N1 first, land S1 -> S2 -> S3, never tornado,
   and use only authored return transit if another cycle occurs.
5. Save at S1, S2, and S3, advance, load, and verify the restored tracer chooses
   the correct next destination without a separate route counter.
6. For the Ricco launcher, test success on attempts 1/2/3 and exhausted pools;
   confirm totals `3/4/5` and all-failed `3` selectors plus zero velocity calls.
7. Load every Ricco episode/region and match all five crane names. Confirm all
   five 20-value speed bands, per-crane stability, live band remapping, fresh
   rolls after stage reload, and exact retail restoration from Off.
8. Enable each boss control during an eligible IL. Confirm credit is revoked,
   Creation is locked, every supported HUD/overlay foreground and FLUDD water
   turns pure red, and `INVALID IL` remains above all overlays. Turn every
   control Off and verify exact colour restoration, including after restarting
   the same scenario and loading an assisted savestate. Confirm successful
   Spawn Yoshi/Regrab actions revoke credit without the persistent warning,
   while failed/no-op binds do not.
9. Test multiple same-type birds and prove actor-aware selection affects only
   the intended pointer/type. Confirm registry reset around stage setup if that
   UI is implemented.
10. Test model water against actors, ground, wall, pool, water surface, and at
   least one non-FLUDD producer. Ground/wall survival is gameplay state.
11. Verify bath manager/children and wave phases repeat under current same-scene
    savestates. Test the two JPA globals only if that optional capture is added.
12. Verify the CARD private `next` and all four audio RNG states remain
    unchanged by every gameplay RNG operation.
